## What the API exposes — and what it does not

This section is fixed regardless of when the extract runs, and it is the honest boundary of what
this document will ever be able to assert.

**Readable via the Airtable Metadata API — will appear below once the extract runs:**

- Every table: name, id, description, primary field
- Every field: name, id, type, and the complete option list for single/multi selects
- Field configuration: link targets, lookup/rollup source chains, formula result types, precision, date formats
- Every **grid / calendar / gallery / kanban / timeline / form** view: name, id, type, parent table, and visible field ids
- Table-to-table relationships, derived from link fields and their inverse pairs

**Not exposed by any public Airtable API — will be absent below, and that absence means nothing:**

- **Interface Designer layouts.** Pages, groups, tab navigation, field label overrides, button
  actions, and conditional-visibility rules are not readable through the API at all. All three build
  specs are almost entirely about interface layout, so most of what they describe **cannot be
  verified here** — only the underlying base fields they depend on can. Interface findings are
  therefore limited to "the field this page needs exists / does not exist".
- **View configuration beyond name, type, and visible fields** — filters, sorts, groupings, row
  height, and colour rules are not returned.
- **Automations.** Names, triggers, actions, and scripts (AX09, AX23, AX24, and the rest) have no
  read endpoint.
- **Personal views**, and any view belonging to a collaborator other than the token owner.
- **Base-level permissions, collaborators, sync configuration, and revision history.**

Verifying the interface layer means opening Interface Designer by hand. Where a spec claims an
interface behaviour, this document can only confirm the data model underneath it.

## Sample records

Up to 5 records will be read per table **purely to observe record shape**. Every value is replaced
by a type descriptor before it reaches this file — no field value from the base is reproduced
anywhere in this document. No SSNs, no credit data, no contact details.

| Descriptor | Meaning |
| --- | --- |
| `—` | cell was empty |
| `text(len 24)` | a 24-character string was present, and discarded |
| `number(int)` / `number(decimal)` | a number was present; **magnitude is never reported**, so a credit score and a funding amount look identical |
| `checkbox` | a boolean was present; **which way it points is never reported** |
| `linked[3]` | a link cell holding 3 record ids |
| `attachment[1]` / `collaborator[2]` | attachment or collaborator cells, counted only |

Select cells report only that a choice was made, never which one. Record ids are kept: they are
opaque handles, not client data, and they let a reader match a sampled row against a link column in
another table. Raw records are never written to disk in any form — `describeValue()` in
`scripts/extract-airtable.mjs` is the only thing between the API response and this file, and its
redaction behaviour is covered by assertions.

## How to populate this file

The extractor is complete and its pure logic is verified against a mock base (schema shaping,
relationship dedup, redaction, spec checks, and document rendering). It needs only network reach.

**Either** allow `api.airtable.com` in this environment's network egress settings and re-run here,
**or** run it anywhere with outbound access to Airtable:

```sh
export AIRTABLE_API_KEY=pat...      # never commit this, never pass it as an argv
export AIRTABLE_BASE_ID=appXsq65yB9VuNup5
node scripts/extract-airtable.mjs               # writes this file
node scripts/extract-airtable.mjs --stdout      # print instead
node scripts/extract-airtable.mjs --no-samples  # schema only, no record reads
```

Behind an HTTPS proxy, prefix with `NODE_USE_ENV_PROXY=1` — Node's built-in `fetch` ignores
`HTTPS_PROXY` without it.

The token is read from the environment only. It is never written to this file, never logged, and
never interpolated into an error message. The required PAT scopes are `schema.bases:read` and
`data.records:read`; `schema.bases:read` on the whole workspace additionally resolves the base's
display name, and a base-scoped PAT that cannot list bases degrades gracefully.

Running the script overwrites this file in full, replacing this placeholder with the real extract:
a section per table with fields, types and full option sets, views, relationships, redacted sample
shapes, and the mismatch report described below.

## Spec mismatches — what will be checked

are **flagged, never fixed**: the specs say what was supposed to be built, the extract says what
exists, and reconciling the two is a decision rather than a cleanup.

Findings are classified as **Table missing**, **Field missing**, **Type mismatch** (spec treats a
field as a select but the base type has no options), or **Option set differs** (in both directions —
choices the spec expects that the base lacks, and choices the base carries that no spec mentions).

Table and field names are matched case- and separator-insensitively, so `INQUIRY_REMOVAL_CASES`
