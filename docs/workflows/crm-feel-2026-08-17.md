# CRM feel — 2026-08-17

Owner report: the CRM feels janky. Five things, all believed shared-stylesheet level.

1. Clicking around causes loading and glitching. Panels jump.
2. It zooms in and out slightly — inconsistent scaling.
3. When zoomed out the layout doesn't scale. Panel edges show as visible seams
   instead of one surface. Owner works zoomed out.
4. The font is small.
5. Overall it feels barely hanging together, not like expensive software.

Owner instruction: measure on the live site first. Find the real causes. Do not
assume the owner's list is complete. Fix in the shared stylesheet where possible,
not screen by screen. Standing GO. No invented data.

## Findings

Full detail in `crm-feel-2026-08-17-evidence/w1-findings.md`, `w2-findings.md`,

**All three measurement agents were blocked from signing in.** Live login was

### Causes fixed in this batch (shared stylesheets only)

| Owner complaint | Real cause | Fix |
|---|---|---|
| Font is small | body 14px / caption 11px, all absolute px. At the owner's 67% zoom the 11px floor painted 6 real px. Zero rem/em/%/clamp/vw in all ten stylesheets. | Tokens restated in rem; body 16px, caption 13px, title 20px, metric 32px |
| Zooms in and out | `.app-shell` was missing from the type-snap selector list, so my-numbers got no snap: sidebar text 11px there vs 14px elsewhere, nav block 119px shorter. The rail is on every screen, so it is the ruler the eye uses. | `.app-shell` added; list rewritten with `:is()` so a wrapper cannot be added to one list and forgotten in the others |
| Panels jump | `crm-sidebar.css` loads twice (shell.js:599 guards on an id the page's own `<link>` does not carry). Its `display:block` beat the six screens' own `display:flex` ~9ms after paint — a measured 362px jump on staff-teams, every load. | `display` declaration removed, making the second load a no-op |
| Panels jump | `--fh-statusbar` started at 0px and was overwritten at runtime by data.js:497, growing the page ~29px after paint | default raised to 32px so the space is reserved up front |
| Panels jump | rail animated width over 182ms while `.app` padding-left snapped in 7ms, so the rail covered ~168px of content on the way | `.app`/`.app-shell` now transition padding-left in step; reduced-motion honoured |
| Doesn't scale zoomed out | content capped at 1280px with a fixed 228px rail: 1052px (41.1%) of a 2560 screen empty, and no breakpoint above 1201px anywhere | `--fh-maxw` 1280 -> 1800 (owner-set). Measured after: 1800 at 2560, 1692 at 1920, unchanged at 1440 |
| Visible seams / not expensive | panels #FFFFFF on a #FCFCFC page — a 9-point step, too small to read as deliberate; and no resting shadow anywhere in the app | page moved to `--field` (#F4F4F5, existing `--soft` token) and one soft resting shadow added to the measured panel classes |

### Found and deliberately NOT fixed (out of the owner's scope)

- Every nav click is a full page reload; 6 files re-fetched per click, 197-2474ms of white screen (`shell.js`, `public/_headers`). Not a stylesheet problem.
- The BETA bar lands after paint and shoves the page down 62px — CLS 0.346 on command-center. Owner has already ruled the bar stays; the fix is to stop it landing late, which is JS.
- Sidebar paints 33 rows then snaps to 3; top-right chrome rebuilt after paint (589px slide).
- 598 off-8px spacing declarations (85% of all spacing), 14 distinct corner radii, headers differing six ways, 1px pure-black pane seams, closer-dashboard full-bleed while five others are capped. All per-screen work.
- No loading skeletons exist anywhere (UI-STANDARDS §6 requires them).

### Hypothesis raised and killed by measurement

- Scrollbar width changing between screens: measured 0px in four browser modes on macOS. Would be 15-17px on Windows. `scrollbar-gutter` is set nowhere; cheap insurance if staff use Windows, but not the owner's cause.
- CSS `zoom`, `transform:scale`, `text-size-adjust`, differing viewport tags, differing root font-size: all ruled out by direct measurement. Root is 16px on every screen at every width.
