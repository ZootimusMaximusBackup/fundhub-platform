# The live site would not let anyone sign in for 27 minutes

**When:** 2026-08-17, 8:33 pm to 9:00 pm local time (2026-08-18 03:33–04:00 UTC).
**Where:** https://fundhub.ai (the real site, not a test copy).
**Now:** fixed itself at 04:00 UTC. The capture ran straight after and worked.

## What happened

The plan was simple: sign in as the owner, open Campaigns, pick a partner from the
Partner box at the top, and take pictures of the screen. Step one never worked.

Signing in failed. The site's sign-in returned an error:

```
POST https://fundhub.ai/api/auth/login  →  500
{"ok":false,"error":"internal_error","message":"cannot execute INSERT in a read-only transaction"}
```

Plain English: the database was in "look but don't touch" mode. It would answer
questions, but it would not let anything be written down. Signing in has to write
a row, so signing in could not finish.

An older sign-in that was still saved on this machine did not help either. Every
page a signed-in person loads first asks "is this person still signed in?", and
that question also writes a row (`src/auth/session.mjs` line 78 runs an `UPDATE`
on the `sessions` table). So it failed too:

```
GET https://fundhub.ai/api/auth/session          →  503  {"ok":false,"error":"auth_unavailable","db":"down"}
GET https://fundhub.ai/api/read/partners?limit=200 → 503  {"ok":false,"error":"auth_unavailable","db":"down"}
```

The browser then bounced to the sign-in page. That is the picture saved here as
`outage-bounced-to-login-1440.png` — it is the sign-in page, not Campaigns.

## The confusing part

The site's own health check said everything was fine the whole time:

```
GET https://fundhub.ai/api/health → 200
{"ok":true,"db":"up","state":"up","migrations":159,"expected":156,"pending":0}
```

That check only reads. Reading worked. Writing did not. So the health check said
"up" while nobody could sign in.

## Who this affects

Everyone, not just this capture. While it lasted:

* Nobody could sign in — staff, owner, clients, partners, affiliates.
* Anyone already signed in saw "backend unavailable" instead of their screens.

## What was checked and when

| Time (UTC) | Check | Answer |
|---|---|---|
| 03:33 | sign in as owner | 500 · "read-only transaction" |
| 03:35 | health | 200 · "db up" |
| 03:35 | saved sign-in → partner list | 503 · "db down" |
| 03:36–03:42 | partner list, every 25 seconds, 15 times | 503 every time |
| 03:43–03:59 | partner list, every 30 seconds | 503 every time |
| 03:58 | sign in as owner, second try | 500 · "read-only transaction" |
| 04:00 | partner list | **200 · working again** |

## One more thing worth knowing

While this was going on, the site's own health line showed the number of applied
database updates climbing: 159 at 03:35, then 162 at 03:58. Something else was
deploying to the live site during the outage. Three new database update files
were added to this repo at the same time (`174`, `175`, `176` in `db/migrations`,
saved 8:36–8:42 pm local). That is another workflow's work, not this one's, and
it is only noted here because the timing lines up.

## What was captured afterwards

Everything that was missing. The script at
`docs/workflows/campaigns-readable-2026-08-17-evidence/_tools/campaigns-before.mjs`
ran at 04:00 UTC and wrote the 1440-wide and 390-wide pictures, the page's words
as text files, and a row count for every panel into this folder.
