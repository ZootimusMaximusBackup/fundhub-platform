# W3 — on-demand soft pulls

`status: done` · branch `claude/finance-os-softpulls` · PR #39

## What changed, in plain language

The system can now record that somebody asked for a client's credit to be
checked, and it can store the answer when it comes back. Before this, only the
answer was kept — nothing said who wanted it or why.

Two new pieces landed in this second pass:

* **`recordPull`** — a credit check came back. Store it, and put the cards it
  found where the closer's calculator reads them.
* **`getLatestPull`** — the most recent credit check for one client.

**Nothing sends anything.** No credit bureau is contacted anywhere in this work.

## Decisions made (no questions asked, per the autonomy rules)

1. **A text reason is sufficient authorisation for now.** The person tapping has
   to type why. The client does not have to have signed anything. This is
   FLAGGED, not resolved — see the compliance note.
2. **`recordPull` accepts pulls with no ledger request.** The paid path
   (`diagnostic.paid` → C-00) predates this ledger and files no request. A pull
   that happened is a fact; refusing to store one for want of paperwork would
   lose the only copy.
3. **An empty payload is refused.** Storing `{}` would put a row in the history
   reading "we checked and they have no credit" — a different and much worse
   claim than "the check failed", which is what `closeSoftPull(status:'failed')`
   is for.
4. **`getLatestPull` returns the row as stored and does not parse it.** Callers
   who want the cards read `tradelines`, which `recordPull` already filled
   through the one existing normalizer.
5. **Roles:** owner, admin, closer, funding advisor, plus a client acting on
   their own file only. Setters and inquiry specialists refused.

## COMPLIANCE — flagged, not blocking

Whether a typed reason is enough, or whether the client must also have signed a
consent record, is a human decision. A consent document kind already exists
(`soft_pull_consent` in `src/documents/kinds.mjs`) and there is a standing open
finding that the paid path never checks it either. Shipping anyway per the
autonomy rules; the ledger records enough to answer the question either way.

## Finding: `src/db.mjs` exports a handle that cannot open a transaction

`export const db = { query }` — **no `connect`**. Every `withTransaction` helper
in this repo probes `typeof db.connect === "function"` to decide whether to open
a transaction, so with the shared handle it silently takes the **no-transaction**
branch and runs with autocommit.

Caught by a test, not by reading: a pull naming an already-resolved request left
an orphan `crs_results` row behind, because the INSERT had committed itself
before the failure was raised.

**This is not only my module.** `src/pii/index.mjs` `revealSsn()` has the same
probe and the same handle, so its rule 3 — *"the access log is written in the
same transaction as the reveal; if the log write fails, the reveal fails"* — does
not hold as shipped. That is a documented compliance control that the code does
not implement.

I fixed it inside `src/finance/soft-pulls.mjs` only, and deliberately did NOT
touch `src/pii/**`: changing the transaction behaviour of an SSN-disclosure path
is a behavioural change to a compliance-critical control and deserves its own
review, not a drive-by from a parallel workflow. **Somebody should pick this up.**
