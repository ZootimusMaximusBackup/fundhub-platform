# W6 — Card liabilities (what a client owes on each card, and how it has moved)

Status: **done**
Branch: `card-liabilities-w6`
Owner: W6

---

## What changed, in plain language

We already store each of a client's credit cards: who the lender is, how big the
line is, and roughly what is owed. That is the "card" record.

This adds a second, different record: **the bill**. For each card we can now keep
what the statement closed at, what the smallest payment is, when it is due, how
much is past due, and what was paid last. And we keep **every one of those, month
after month**, so you can see whether a client's balances are going up or down
instead of only seeing today's number.

Two new places to put that:

* **The current bill** — one row per card. This is what a screen would show.
* **The bill history** — every bill we have ever seen on that card, kept forever.

Nothing sends anything anywhere. There is no screen, no button, no scheduled job.
This is only the storage and the code that reads a credit-pull file into it.

### The three things we were careful about

1. **"We don't know" is never turned into "$0."** If a credit file does not say
   what the smallest payment is, we store *unknown*, not zero. Storing zero would
   put "$0 due" in front of a client, which is us telling them nothing is owed.
2. **Interest rates are stored one way only.** 18.99% is stored as `0.1899`,
   never as `18.99`. The database itself now refuses the wrong form, so even a
   future mistake in code cannot get a 1,899% rate into a client's record.
3. **Money is stored in whole cents.** No decimals. This is the same defect that
   already bit us once elsewhere in this codebase, where a commission came out a
   penny short because it was calculated with decimals.

## Decisions, and why

| Decision | Why |
|---|---|
| A separate table from `tradelines` rather than more columns on it | `tradelines` is the **card** (lender, limit, rate). This is the **bill** (minimum payment, statement date, due date, past due, last payment). Six of the new measures have no counterpart anywhere in `tradelines`, and `tradelines` keeps no history at all — every pull overwrites it. |
| Two tables (current + history), not one | The question every screen asks is "what is owed now" — that should be one indexed row, not a sort over a growing series. The question "how has it moved" is rarer and needs everything. History is the source of truth; the current row is a projection of its newest entry and can be rebuilt from it. Both are written in one transaction, so there is no code path that writes one and not the other. |
| Ordering key is **`as_of`** (when the position was true), not `created_at` (when we wrote it) | A pull run Monday and loaded Wednesday describes Monday. Ordering on write time would crown a late-arriving old statement as "current" and show a client a balance weeks out of date. |
| Ties on the same `as_of` break by `created_at DESC` | The same statement date read twice is a bureau **restating** it. The later read is the correction. |
| The current row **never moves backwards** | The write carries `WHERE EXCLUDED.as_of >= card_liabilities.as_of`. Backfilling an old statement lands in the history and leaves the current position alone. |
| `as_of` is *our observation date* and is required; `statement_date` is the bureau's and is optional | We always know when we looked. The bureau's statement close date is a separate fact that a file may simply not carry. Conflating them is what makes a stale backfill look current. |
| Reused `readApr()` from `src/tradelines/index.mjs` rather than writing a second one | It already solves the hard problem — bureau files carry the rate as both `18.99` and `0.1899` under the same field name — and it refuses anything it cannot read instead of clamping it. Two readers of one payload is the defect class this repo keeps finding. |
| Reused `withTransaction()` from `src/documents/register.mjs` | It already handles the three database-handle shapes this repo passes around. Writing a fourth copy is the same duplication problem. |
| An unrecognised payment status reads as **unknown**, never as "current" | Guessing "current" on an account in collections is the expensive direction to be wrong in. (This is the opposite default from `readKind()` next door, and deliberately so.) |
| A credit-pull record whose account number matches no known card is **skipped and counted**, not turned into a new card | This module owns bills, not the card list. Creating a card here would put a second writer on a table `src/tradelines/store.mjs` already owns. |
| No delete-blocking trigger on the history table | This is consumer personal data on a cascade from `clients`. A hard no-delete trigger (like the one on `commission_ledger`) would abort a client-deletion request. Append-only is enforced by the write path and asserted by the tests. |

## Schema added — for W10 and anyone consuming this

### `card_liabilities` (migration `083_card_liabilities.sql`)
One row per card. The bill that stands right now.

| Column | Type | NULL means |
|---|---|---|
| `id` | uuid PK | — |
| `org_id` | uuid NOT NULL → `orgs(id)` | — |
| `client_id` | uuid NOT NULL → `clients(id)` ON DELETE CASCADE | — |
| `tradeline_id` | uuid NOT NULL → `tradelines(id)` ON DELETE CASCADE | — |
| `as_of` | date NOT NULL | — (our observation date; the ordering key) |
| `statement_balance_cents` | bigint, CHECK ≥ 0 | not reported |
| `current_balance_cents` | bigint, CHECK ≥ 0 | not reported |
| `minimum_payment_cents` | bigint, CHECK ≥ 0 | **not reported — never render as $0** |
| `past_due_cents` | bigint, CHECK ≥ 0 | not reported (a reported `0` is a different, real fact) |
| `last_payment_cents` | bigint, CHECK ≥ 0 | not reported |
| `last_payment_date` | date | not reported |
| `statement_date` | date | the file did not carry a statement close date |
| `payment_due_date` | date | not reported |
| `apr` | **numeric(6,5) CHECK (apr >= 0 AND apr <= 1)** | no rate reported, or one the parser refused to guess at |
| `payment_status` | text CHECK in `current, late_30, late_60, late_90, late_120, charge_off, collection` | the file did not say, or said something we have not confirmed a meaning for |
| `source` | text NOT NULL DEFAULT `'manual'`, CHECK in `crs, manual` | — |
| `source_ref` | uuid → `crs_results(id)` ON DELETE SET NULL | not from a stored pull |
| `raw` | jsonb NOT NULL DEFAULT `'{}'` | — |
| `created_at`, `updated_at` | timestamptz NOT NULL DEFAULT now() | — |

Indexes: `uq_card_liabilities_tradeline` UNIQUE `(tradeline_id)`;
`idx_card_liabilities_client` `(client_id, payment_due_date NULLS LAST)`.

### `card_liability_history` (migration `084_card_liability_history.sql`)
Every bill ever observed. Same measure columns and the same CHECK constraints,
plus:

| Column | Type | NULL means |
|---|---|---|
| `liability_id` | uuid → `card_liabilities(id)` ON DELETE SET NULL | the current-position row was rebuilt or removed; the series survives it |

No `updated_at` — a history row is an observation, not a record under
maintenance.

Indexes: `uq_card_liability_history_asof` UNIQUE `(tradeline_id, as_of)`;
`idx_card_liability_history_series` `(tradeline_id, as_of DESC, created_at DESC)`;
`idx_card_liability_history_client` `(client_id, as_of DESC)`.

## Findings (things worth knowing, not things I fixed)

1. **`npm run lint` and `npx tsc --noEmit` do not exist in this repo.** CLAUDE.md
   §6 requires both before a task can be called done. `package.json` has only
   `migrate`, `artifact`, `diagrams`, `diagrams:check`, `test`, and there is no
   TypeScript config. Reported rather than invented.
2. **`docs/journeys/` does not exist.** CLAUDE.md §4 describes journey diagrams
   and a changelog under that path; the directory is not in the repo. Nothing to
   update, and nothing here is wired to a user-facing flow anyway (no route, no
   screen, no scheduled job).
3. **`withTransaction` already exists twice** — exported from
   `src/documents/register.mjs` and duplicated privately inside
   `src/inquiries/work.mjs`. I imported the exported one. The duplicate is
   pre-existing and out of my scope to touch.
4. **A credit balance (an overpaid card) reads as unknown, not as a negative.**
   The money columns carry `CHECK (>= 0)` to match `tradelines`, and `toCents()`
   already returns null for a negative. Rare, but it is a real reading we drop.
   Deliberate, documented, and worth a decision later.
5. **Historical utilization cannot be computed from this table alone.** I did not
   copy `credit_limit_cents` here, because a limit is a property of the card, not
   of the bill, and 054's header is explicit that derived and duplicated values
   are what go stale. If a future screen wants "utilization over time", the limit
   as-of a date is a gap that has to be filled deliberately.
6. **Nothing consumes this yet.** No endpoint, no route in
   `netlify/functions/api.mjs`, no UI, no event handler.

## Compliance

**No compliance flag raised for this change as it stands.** It adds storage and a
parser; it does not change dispute logic, credit-repair messaging, fee timing,
refunds, payment rails, consent capture or credit-pull type, and it displays
nothing to anyone.

**A flag becomes required the moment any of these numbers reaches a consumer.**
`minimum_payment_cents`, `past_due_cents`, `statement_balance_cents` and
`payment_due_date` are statements about what a person owes and when. Showing them
is a consumer-facing claim about a debt, and it has to clear compliance before it
ships — including how "unknown" is rendered. It must never render as `$0` or as a
blank that reads like `$0`.
