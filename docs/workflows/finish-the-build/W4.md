# W4 — Alerts and upsell rules

**Status:** done
**Branch:** `alerts-upsell-w4`
**Owner:** W4 (one of ten parallel workflows)

---

## What changed, in plain words

Two new places to keep things, and four new rules that do the thinking.

**The two new places (database tables):**

1. **`alerts`** — a list of things the system noticed and wants a person to look at.
   Each row says: what was noticed, which client it is about, who it is for, when
   it was raised, and whether anyone has dealt with it yet.

2. **`upsell_triggers`** — the settings that decide when the system is allowed to
   notice something. Think of it as the dial. Right now every dial is **switched
   off** and **left blank on purpose**. Nobody has told me what the right number
   is, so I did not make one up.

**The four new rules (small pieces of maths):**

1. **How much of a credit card is used up** — the balance divided by the limit.
2. **Where a credit score sits** — which band a number falls into.
3. **Is there a case for a better card** — looks at the client's own cards and
   says whether it is worth a conversation.
4. **A monthly summary** — adds all of the above up for a list of clients.

These four are deliberately "dumb" in a good way. They do not go and fetch
anything, they do not look at the clock, and they never touch the database. You
hand them numbers, they hand back an answer. That means they can be tested in
under a second with no database running, and the answer is the same every single
time you ask.

---

## The one thing that matters most

**"We don't know" never turns into "zero" and never turns into "fine."**

If a card is missing its credit limit, the system says *unknown*. It does not
quietly call it 0% used — which would look like great news and would be a lie.

Every answer these rules give is one of three things: **yes**, **no**, or
**we cannot tell**. Not two. That third one is the whole point, and 20 out of 20
sabotage tests below were built to prove it stays that way.

## Decisions I made, and why

### 1. `upsell_triggers` holds the settings, NOT a list of things that fired

The name could have meant either. It holds the settings.

**Why:** the list of things that fired already exists — that is the `alerts`
table. If both tables kept a record of a firing, the two would eventually
disagree, and nobody would know which one to believe. One list, one truth.

### 2. Every setting ships switched off and blank

`enabled` starts as **off**. The threshold number starts **empty**. The migration
adds **zero rows**.

**Why:** a rule that arrived switched on would start flagging real customers'
credit the moment it landed, based on a number nobody chose. This matches how
`src/mail/` already behaves in this repo — it is finished, and it deliberately
sends nothing until a human says go.

### 3. The 30% number is borrowed, not sourced. Say so out loud.

30% is already in this codebase, in the closer's funding calculator
(`src/calculators/deal-funding.mjs`), where a comment calls it "per-org
configurable" — and no per-org setting existed until now.

**It has no outside source. It is not a number a credit bureau published.** It is
an operating habit this business already runs on. I reused it so there is one
number instead of two, and I wrote plainly in the code that it is borrowed. A
test now checks the two places agree, so they cannot drift apart quietly.

### 4. The credit score bands are NOT my invention

They come from this repo's own `src/config/survey-qualification.mjs`, which
records them as coming from the 05/30 source-of-truth document:
`500-579`, `580-649`, `650-699`, `700-749`, `750+`.

I did not retype those numbers. The code reads them straight out of that file and
works out the edges from the labels. Change the survey options and the bands
follow automatically. Two lists that must agree is a bug waiting to happen.

The rule for which bands are good enough to book a funding call is also that
document's rule, read from the same file.

### 5. The score rule refuses to say "good" or "bad"

It returns which band a number is in. That is all. It will not call a score
"excellent" or "poor."

**Why:** the moment a judgement about someone's credit is written down, it is one
screen away from being shown to that person. This is a regulated money product.
A sentence like that needs a human to approve it, not a default setting.
(See the compliance note at the bottom.)

### 6. Partly-missing data gives a partly-missing answer

If a client has five cards and one of them cannot be read, the system will not
tell you their overall card usage. It shows you the part it can see, clearly
labelled as only part.

**Why:** the missing card could be a huge unused limit (which would pull the
number down) or a maxed-out one (which would push it up). Answering on 4 out of
5 cards is a guess wearing a measurement's clothes.

### 7. Sitting exactly on the line does not set anything off

Exactly 30.00% used is not "over 30%." One cent past it is.

**Why:** it matches the funding calculator already on the closer's screen, and
the comparison is done in whole numbers so a rounding wobble in the computer's
maths can never flip the answer.

## What I did NOT build, on purpose

* **No timer, no scheduler.** Nothing runs on its own. These rules only answer
  when something asks them.
* **No sending.** No email, no text, no notification. **Nothing in this repo
  transmits** and I did not add the first thing that does. An alert row is a note
  for a person, not a message to a customer.
* **No screens and no web addresses.** No user interface, no new pages.
* **No prices touched.** Nothing to do with money owed or charged.
* **No cooldown or "last fired" columns.** Those are timer parts, and there is no
  timer. Duplicate alerts are already prevented a simpler way (see below).

## Findings — things I noticed and did not fix

**1. A missing card balance becomes zero on the way to the funding calculator.**
In `src/tradelines/index.mjs`, the helper `toCalculatorCards()` turns a card with
an unknown balance into a card with a balance of £0. So a card nobody has
measured looks like a card with nothing owed on it. My rules read the raw table
rows instead, where the "unknown" survives — but anything reading through that
helper still sees a zero. **Not fixed: that file belongs to another unit.**
It is written up in the code comments where it matters.

**2. `tradelines.updated_at` has never moved.** Migration 054 added the column but
never attached the little bit of plumbing that keeps it current, so that date is
frozen at whenever each row was created. I attached it correctly on my two new
tables. **Not fixed on `tradelines`: not my file, and changing it is a separate
decision.**

**3. This repo has no `lint` command and no TypeScript setup.** The "definition of
done" checklist asks for both. Neither exists to run. Nothing to fix; noting it so
nobody assumes I skipped a step.

**4. There is no `docs/journeys/` folder on `main`.** The checklist asks for
journey diagrams to be updated. There are none in this branch to update, and I did
not create the folder — that is a repo-wide decision, not a W4 one.

## Table and column names

**`alerts`** — `id`, `org_id`, `client_id`, `tradeline_id`, `assigned_to`,
`kind`, `severity`, `state`, `title`, `detail`, `dedupe_key`, `as_of`,
`raised_at`, `acknowledged_at`, `acknowledged_by`, `resolved_at`, `resolved_by`,
`dismissed_reason`, `trigger_id`, `created_at`, `updated_at`.

* `kind` is one of: `utilization_threshold`, `score_band`, `upsell_opportunity`.
* `state` is one of: `open`, `acknowledged`, `resolved`, `dismissed`.
  *`dismissed` is deliberately different from `resolved` — a pile of dismissed
  alerts of one kind is the signal that the setting behind them is wrong.*
* `dedupe_key` stops the same problem being raised twice while it is still open.
  A resolved alert does not block the same problem coming back next quarter.

**`upsell_triggers`** — `id`, `org_id`, `rule`, `enabled`, `threshold_bps`,
`threshold_score`, `severity`, `notes`, `signed_off_at`, `signed_off_by`,
`created_at`, `updated_at`.

* `rule` is one of: `utilization_over_threshold`, `score_below_threshold`,
  `card_upgrade_case`.
* `threshold_bps` is a whole number, not a decimal — 3000 means 30.00%. Whole
  numbers are used because decimals lose pennies, which is a bug this repo already
  has elsewhere and I was not going to add a second one.
* `signed_off_at` empty means nobody has approved this setting yet. Copied
  straight from how `052_config_defaults.sql` already does it.

## Functions added (for the next workflow that needs them)

All in `src/alerts/evaluate.mjs`:

```
evaluateUtilization(lineOrLines, { threshold })  -> { known, reason, utilization, over, ... }
evaluateScore(score)                             -> { known, reason, band, meetsFundingCallGate }
suggestCardUpgrade(lines, { threshold, targetAmountCents })
                                                 -> { suggest, reasons[], estimatedAnnualSavingCents }
monthlyReport({ period, clients, alerts, threshold })
                                                 -> { period, clients[], totals{} }

thresholdFromBps(bps)      -- 3000 -> 0.30. The only place that conversion happens.
readLine(line)             -- reads a tradelines row OR a calculator card
DEFAULT_UTILIZATION_THRESHOLD, SCORE_BANDS, SCORE_MIN, SCORE_MAX, UPGRADE_REASONS
```

`over`, `suggest` and `meetsFundingCallGate` are all **three-valued**: `true`,
`false`, or `null`. **`null` means "cannot tell" — it does not mean "no."**
Code that writes `if (!result.over)` has a bug.

## Compliance

Flagged for a human before any of this is shown to a customer.

Nothing here talks to a customer today. But two of these rules produce sentences
*about a person's credit*, and this is a regulated money product:

* the score rule says which band someone is in;
* the card rule says there is a case for a better card, with a money figure
  attached.

Those are claims about a credit outcome the moment they appear on a screen a
client can see. The code refuses to add adjectives ("good", "excellent") for this
exact reason, and the tables carry warnings on the relevant columns. **A human
signs this off before any of it is shown to a client.**

The money figure is worth calling out plainly: it is one year of the difference
in interest rate on a balance the client already has, comparing the client's own
cards to each other. It ignores fees, promotional rates, and whether a balance
transfer would even be approved. **It is arithmetic on today's numbers, not a
promise of money saved.**
