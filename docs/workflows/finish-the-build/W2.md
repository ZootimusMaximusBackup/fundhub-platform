# W2 — Subscriptions and cards on file

Branch: `subscriptions-cards-w2`
Status: **done**
Owns: migrations **075** and **076** only.

---

## What changed, in plain words

We added two new places for the system to keep information. Nothing on any
screen changed. Nothing sends anything anywhere. No money moves.

**1. A place to record that a client is on a monthly plan.**
Today the system can record a sale (one payment, one time). It had nowhere to
write down "this person pays us every month for this thing." Now it does. The
record holds: which product they are on, what they agreed to pay each period,
how often the period repeats, when it started, when it ends, and whether it is
still running.

**2. A place to record a card the client has said we may bill.**
Not their credit report. Not a sticky note in a pipeline. A card on file.

**What we store about that card: nothing that could be used to buy anything.**
We store a *token* — a meaningless-looking code that a payment company hands
back in place of the card number, and which only works inside that company's
system. Next to it we store the brand ("Visa"), the last four digits, and the
expiry month and year, so a human can tell one card from another. That is all.

**What we do NOT store, and cannot store even by accident:**

* The card number. There is no column for one, and the two places someone might
  try to hide one are blocked by the database itself: the "last four" box
  refuses anything that is not exactly four digits, and the token box refuses
  anything that is not already scrambled.
* The three digits on the back (the CVV). There is no column and there never
  can be one — the card networks forbid keeping it.
* The code also refuses to scramble-and-store a card number if one is ever
  handed to it. Scrambling a card number is still keeping a card number.

The token itself is scrambled before it is written down, using the same method
this system already uses for social security numbers and advertising logins. It
is locked to one client: if the scrambled value is ever copied into a different
client's row, it stops working rather than quietly billing the wrong person.

## The three "card" tables — read this before touching anything

The word "card" now means three different things in this database. They are
deliberately separate, and each one now carries a note inside the database
saying which it is.

| Table | What it is | Can it move money? |
|---|---|---|
| `cards` (001_init) | A client's position on a sales board. A sticky note. | No |
| `tradelines` (054) | Credit-report data: lender, limit, balance, interest rate. A description of a card the client has somewhere else. | No |
| `client_cards` (076, new) | A card the client has authorised **us** to bill. Holds the scrambled token. | Yes, if a payment company is ever connected |

A tradeline is an **observation**. A `client_cards` row is a **capability**.
A client usually has fifteen tradelines and one card on file. The tradeline
import overwrites its rows wholesale on every new credit pull; if billing
credentials lived in that table, that import would one day wipe or rewrite the
card we bill, from code written by someone thinking about credit limits.

## Decisions made, and why

1. **Two tables, not one.** Reasons above. Merging them would put a billing
   credential inside a table that a bulk import overwrites.

2. **Kept the name `client_cards`, even though migration 054 says the opposite.**
   054's header says "the name collision is why this table is `tradelines` and
   not `client_cards`". That sentence was rejecting `client_cards` as a name for
   *credit-report* data. It was not reserving the name. Since editing an applied
   migration does nothing (the runner keys on the filename), 054 cannot be
   corrected. Instead, 076 writes a note onto all three tables inside the
   database, which is what anyone inspecting the schema will actually see. **This
   is the residual risk on this branch:** a person reading 054 in isolation could
   still be misled for about thirty seconds.

3. **The price lives on the subscription, not read from the product.**
   Migration 010 is explicit that a product's price is a *suggestion* for the
   sale form and never what anybody owes. This copies that split exactly.
   Re-pricing a product cannot restate what an existing subscriber owes.

4. **Money is whole cents (`bigint`), like `tradelines` and `soft_pull_requests`.**
   A monthly amount gets multiplied by a period count and added up across every
   subscriber; the older dollars-and-decimals columns round wrong when you do
   that. New table, so it starts correct.

5. **An unknown price stays unknown.** `price_cents` has no default. Empty means
   "we do not know yet", never "free". Defaulting it to zero would put "this
   subscriber owes nothing" into a revenue report nobody re-checked.

6. **Only four statuses: draft, active, paused, canceled.**
   * No `past_due` — reaching it requires a failed charge, and there is no
     charge path anywhere in this system. Migration 077 makes the same call
     about `sent` for the same reason. A status nothing can reach is a promise
     the schema cannot keep.
   * No `expired` — that is simply "the end date has passed", worked out when
     the row is read. Migration 031 dropped `overdue` on exactly this reasoning.
     Storing it guarantees rows that are finished in fact and "active" in the
     database.

7. **Period dates are recorded, never advanced.** Nothing in this build rolls a
   billing period forward, because that is the billing engine's job and there is
   no billing engine.

8. **The link between a plan and its card is added in 076, not 075.**
   075 runs first, when `client_cards` does not exist yet. Declaring the link
   there would make the migration fail on a fresh database. 076 adds it once it
   can see its own table.

9. **No link to `soft_pull_requests` (077).** That is another workflow's table
   and it is not on `main` yet. Adding the link from here would break whichever
   migration ran first. It is a separate, later, deliberate migration.

10. **No payment company is named.** None is named anywhere in this repository —
    not in the schema, not in the docs, not in the example environment file.
    So `provider` is free text with no list of allowed values. Writing a list
    here would decide a vendor question, in a migration, which is the worst
    possible place to decide one. **This absence is a finding, not a gap we
    filled with a guess.**

11. **Consent is recorded but not forced.** A `consent_captured_at` date says
    when the cardholder agreed we may bill them again. Empty means **no recorded
    consent**, which is unknown and must never be read as permission. It is not
    required, because forcing it would manufacture a consent record for any card
    brought in from elsewhere — exactly the record an audit needs to be honest.

12. **Removing a card destroys the token.** The row survives (so a past charge
    stays explicable) but the database refuses to let a removed card keep its
    credential. A soft delete that leaves the credential in place is not a
    removal.

## Schema added — other workflows need these names

### `subscriptions`

`id`, `org_id`, `client_id`, `product_id`, `plan_label`, `status`,
`price_cents`, `currency`, `billing_interval`, `billing_interval_count`,
`started_at`, `ends_at`, `current_period_start`, `current_period_end`,
`canceled_at`, `cancel_reason`, `default_card_id`, `provider`, `external_ref`,
`notes`, `created_at`, `updated_at`

* `status` ∈ `draft | active | paused | canceled` (default `draft`)
* `billing_interval` ∈ `day | week | month | year` (default `month`)
* `price_cents` is `bigint`, nullable, **no default** — NULL means unknown
* `ends_at` NULL means **open-ended**, not unknown (the one place in these two
  tables where NULL is a positive fact)
* Constraints: `subscriptions_status_check`, `subscriptions_price_cents_check`,
  `subscriptions_billing_interval_check`,
  `subscriptions_billing_interval_count_check`, `subscriptions_period_order`,
  `subscriptions_term_order`, `subscriptions_canceled_needs_stamp`,
  `subscriptions_default_card_fk`
* Indexes: `idx_subscriptions_client`, `idx_subscriptions_org_status`,
  `uq_subscriptions_active_plan` (unique, partial on `status = 'active'`)

### `client_cards`

`id`, `org_id`, `client_id`, `token_enc` (bytea), `brand`, `last4`, `exp_month`,
`exp_year`, `provider`, `provider_customer_ref`, `is_default`,
`consent_captured_at`, `consent_source`, `removed_at`, `removal_reason`,
`created_at`, `updated_at`

* Constraints: `client_cards_last4_check`, `client_cards_exp_month_check`,
  `client_cards_exp_year_check`, `client_cards_token_presence`,
  `client_cards_token_is_ciphertext`
* Indexes: `idx_client_cards_client` (partial), `uq_client_cards_one_default`
  (unique, partial)

### New environment variable

`CARD_TOKEN_ENC_KEY` — 32 bytes, base64. Required before any card can be stored.
A deliberately separate key from `AD_TOKEN_ENC_KEY` and `PII_ENC_KEY`, so an
advertising login, a social security number and a billable credential do not
share one blast radius or one rotation. Without it the code refuses to store,
rather than writing anything readable.

## COMPLIANCE REVIEW REQUIRED

This is a regulated consumer-finance product and this branch adds a table for
stored payment credentials. Flagged under CLAUDE.md §7 for **consent capture**
and **payment rails**.

Stated plainly:

* **Stored:** an encrypted payment-company token; card brand; last four digits;
  expiry month and year; when consent was captured and where it came from.
* **NOT stored, and structurally prevented:** the card number, the CVV, or
  anything from which either could be rebuilt.
* **Nothing transmits.** No payment company is connected, no charge can be
  attempted, no schedule runs.

**A human must confirm the tokenization boundary before any real card is ever
stored.** The assumption this design rests on is that a payment company collects
the card directly from the customer's browser and returns a token — so the card
number never reaches this system at all. If that is not how the chosen payment
company works, this design is wrong and must not be used. Nobody has chosen a
payment company yet.

Also for a human: **consent wording and retention.** The table records *that*
consent happened and *when*. It does not hold the words the customer agreed to.
Whether those words satisfy the card-network rules for repeat billing is a legal
question, not a schema question.

## Findings

1. **No payment company is named anywhere in this repository.** Searched the
   schema, the source, the docs and the example environment file. Nothing.
   That is why `provider` has no list of allowed values.
2. **Migration 054's header now reads misleadingly.** It says the tradelines
   table is not called `client_cards` because of the name collision. A table
   called `client_cards` now exists and means something else. 054 cannot be
   edited (an applied migration is keyed by filename; editing it does nothing),
   so the correction lives in database-level notes on all three tables.
3. **`npm run lint` does not exist.** There is no `lint` script in
   `package.json` and no linter config file in the repository.
4. **`npx tsc --noEmit` does not apply.** There is no `tsconfig.json` and no
   TypeScript in the repository — it is plain JavaScript modules.
   Items 3 and 4 are two of the six checks CLAUDE.md §6 requires; they could not
   be run because they do not exist here.
5. **`.env.example` could not be edited** — this agent's file permissions deny
   writing to dotfiles in the repository root. `CARD_TOKEN_ENC_KEY` is therefore
   documented here and in the migration header, but not yet in that file.
6. **`CARD_TOKEN_ENC_KEY` was not set in Netlify.** CLAUDE.md §11 says a new
   environment variable is the agent's to set. `api.netlify.com` is blocked by
   network policy in this environment (CLAUDE.md §11, Egress), so the command
   cannot run. It must be set by a human before any card is stored — and until
   it is, the code refuses to store rather than storing anything readable, which
   is the safe failure.
7. **`node_modules` is not in `.gitignore`** in this repository. Worth knowing
   for anyone working in a worktree; nothing was committed from it.

## Deliberately left undone

* **No payment-company client, no charge path, no scheduler, no billing engine.**
  Out of scope by instruction and by CLAUDE.md. The seam in
  `src/billing/card-tokens.mjs` is documented and empty.
* **No endpoints and no screens.** Nothing was added to the routes map in
  `netlify/functions/api.mjs`, so there is nothing new to reach and nothing
  routed to nowhere.
* **No store/read module for either table.** Only the encryption helper was
  written, because the encryption rule needed somewhere to live and the schema
  test needed real ciphertext to prove the database accepts it. Writing rows is
  the job of whoever builds the screen.
* **No journey documentation changed.** These migrations add storage only; they
  do not add, remove or reorder a step in any user flow. Nothing in
  `docs/journeys/` became less true, so nothing there was edited and no
  changelog line was appended. Inventing a journey change to satisfy a checklist
  would make the record less honest, not more.
* **No link from `soft_pull_requests.subscription_id`.** Belongs to a later
  migration, once both tables are on `main`.
* **No `plans` table.** A plan here is a product plus a cadence. Inventing a
  separate plans table would have decided a pricing-model question nobody asked
  for.
