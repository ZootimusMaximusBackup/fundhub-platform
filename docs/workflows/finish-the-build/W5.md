# W5 — Bank connections (Plaid): the tables, the locked box, and two empty seams

**Branch:** `plaid-banking-w5`
**Status:** done
**COMPLIANCE REVIEW REQUIRED — SOC 2.** Details in the last section. Read it.

---

## What changed, in plain words

We built the **place** to keep bank information. We did **not** connect to any bank.

Three things:

1. **A table for each bank login.** If someone logs into Chase once, that is one
   "login" row. It holds the secret key that would let us read their account.
2. **A table for each account behind that login.** Checking, savings, a credit
   card — one row each. It holds names, last four digits, and balances.
3. **A field that says whose money it is.** Personal, business, or **we do not
   know yet**. "We do not know yet" is what every new account starts as.

Plus a small piece of code that:

* says whether the settings needed to talk to a bank exist (yes or no),
* locks the secret key so nobody can read it out of the database,
* has two clearly marked **empty spots** where the real bank connection would go.

**Nothing sends anything anywhere.** There is no code in this repo that can reach
Plaid, or any bank, or any outside service. That is on purpose. It stays that way
until a person signs off.

---

## The decision that matters most: "we do not know" is not "personal"

Every bank account we store carries a label saying whose money it is. There are
three possible labels:

* `unknown` — nobody has worked it out yet. **This is what every account starts as.**
* `personal` — someone checked, and it is the person's own account.
* `business` — someone checked, and it belongs to their company.

**Why we did not start accounts as `personal`.** Most bank accounts really are
personal, so `personal` looks like the safe guess. It is the most expensive guess
available. If an account arrives already labelled "personal", nothing later can
tell a guess from a fact — the label looks the same either way. A business
account quietly filed as personal either drags company money into a personal
picture, or hides it from a funding decision entirely. And nobody catches it,
because the field looks filled in. Everyone who looks sees a complete record and
moves on.

So the label starts as `unknown`, `unknown` is a real allowed value, and any code
that needs to know must **ask a human**, not assume.

**One extra rule:** you cannot label an account `personal` or `business` without
also saying **how you know** — the client told us, staff reviewed it, a document
proves it, or the bank said so. The database itself rejects a label with no
basis. A rule that only lives in code is a rule that a bulk data fix walks
straight past.

**What we deliberately did NOT decide:** a "mixed" label, for an account that
holds both personal and business money. Those accounts are real and common. No
document in this repo says how the product should treat one, so we did not invent
an answer. Until somebody decides, a mixed account is honestly `unknown` — which
makes someone ask the question instead of getting it wrong. **This is an open
question for a human.**

## The other decisions

**The bank secret is locked, and an unset lock stops the feature.** The key that
would let us read someone's bank account is scrambled before it is stored, using
the same method the repo already uses for advertising logins and social security
numbers. The scrambling is tied to the specific row it belongs to, so if that
scrambled value were ever copied onto a different person's row it simply stops
working instead of silently handing one person access to another person's bank.
If the lock's own key is not set up, the code **refuses to store anything** — it
never quietly falls back to storing the secret in plain view.

**Unset settings mean OFF, never on.** The repo's own audit found a case where a
missing setting was read as "no check needed", and an outsider could have driven
a client's funding status. So: missing settings, half-set settings, or a
malformed key all report "not enabled". The safe answer, every time.

**"Is it enabled" is not a switch.** It reports whether the settings exist. It
does not turn anything on and it does not hide a half-built feature behind a
flag. Even with every setting present, the two empty spots still say "not built".

**"We did not ask" is not "there are none".** When something asks for a client's
bank accounts, the answer comes back as **nothing/unknown** — not as an empty
list. An empty list would mean "this person has no bank accounts", which is a
fact a funding decision would act on. We must never let a refusal be read as a
fact about somebody's money.

**Where the code lives.** It is in a new folder `src/banking/`, not in
`src/adapters/`. `src/adapters/` is a fixed set of eight inbound message readers,
and an automatic drawing of the system is generated from that folder. This code
reads no incoming messages, so putting it there would draw a connection on that
diagram that does not exist — and would force an edit to a shared file that all
ten parallel branches would then collide over.

## Findings — things a human needs to know

1. **"Mixed" / commingled accounts have no agreed answer.** Not invented. Today a
   commingled account is `unknown`. Somebody has to decide the rule.
2. **The repo now has a third copy of the same encryption code.** `src/pii/`,
   `src/adplatforms/tokens.mjs` and now `src/banking/plaid.mjs` each implement the
   same scrambling with a different key. They must not share a key, but they
   could share one helper that takes the key's name as a setting. That is a
   change across three modules and was out of this workflow's scope.
3. **`npm run lint` and `npx tsc --noEmit` do not exist in this repo.** There is
   no lint script in `package.json` and no TypeScript config file. Two of the six
   "definition of done" steps cannot be run here. Not caused by this work.
4. **`.env.example` could not be updated.** The tooling in this environment
   blocks reading or writing that file, and editing a file without reading it
   first breaks a repo rule. The four setting names are written down above and in
   `src/banking/plaid.mjs`. Somebody should paste them into `.env.example`.
5. **`src/adapters/` is a closed set of eight.** Adding a ninth file there fails
   `adapters report their auth scheme and emitted events` and
   `docs/diagrams is in sync with the code`. Worth knowing before the next
   workflow tries to add one.
6. **No journey diagram changed.** This work adds no screen, no route and no step
   a person walks through, so no `docs/journeys/*-actual.md` file moved and no
   changelog line was added. If a bank-connection screen is built later, that is
   when the client journey changes.

## COMPLIANCE REVIEW REQUIRED — SOC 2

**What this stores.** `plaid_items.encrypted_access_token` is built to hold a
Plaid access token. That is long-lived permission to read a real person's bank
account. `bank_accounts` holds account names, the last few digits of an account
number, and balances. `plaid_items.consent_granted_at` and `consent_scope` are
consent-capture columns — a compliance-flagged area.

**How it is protected.** The token is scrambled with AES-256-GCM (a standard
strong lock) before it goes in the database, and the scrambling is tied to the
exact row it belongs to, so a copied value fails rather than granting access to
the wrong person. The key comes only from an environment setting, never from
code. The token is never logged, never returned in any response, never put in an
error message, and `redactPlaidItem()` strips it before a row can reach a screen.
There is no plaintext token column at all.

**What an unset key does.** It stops the feature. Storing refuses outright and
`isPlaidEnabled()` reports false. There is no fallback to storing the token in
plain view, ever.

**No bank connection can be made.** There is no code path in this repository that
can contact Plaid or any bank. Both connection points are empty and return an
honest "not implemented". `plaid_items` and `bank_accounts` are empty tables and
will stay empty.

**Settings deliberately NOT set.** `PLAID_CLIENT_ID`, `PLAID_SECRET` and
`PLAID_TOKEN_ENC_KEY` were not created in Netlify. The repo's normal rule is that
an agent sets a new setting itself, but that rule assumes the setting turns on
something already approved. Setting these would make the system report that bank
connections are configured, before anyone has approved storing bank credentials
here. That decision belongs to a person.

**Before any of this may be switched on, a human must sign off on:**

1. A **SOC 2** review of storing bank access credentials in this system — key
   management, key rotation, who can reach the database, how long tokens are
   kept, and what happens on revocation.
2. The **consent wording and capture flow** a client agrees to before their bank
   is connected, reviewed by compliance.
3. The **retention and deletion** answer: how long a token and the account data
   live, and what a client's deletion request removes.
4. Whether Plaid is the chosen provider at all, and under which agreement.
