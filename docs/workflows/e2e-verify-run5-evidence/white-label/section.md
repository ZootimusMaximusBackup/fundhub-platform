### Failure blocks (capped)

**white-label · S3 blocked (all groups) — staff-only routes answer 401 "unauthorized" to a signed-in partner, not 403 (LOW)**
- Expected: -actual.md / -intended.md: a recognised principal of the wrong kind is "Refused — 403 forbidden".
- Observed: 92 of 107 probed blocked routes answered 401 unauthorized with a valid partner token (session 200 role=partner). Only 15 answered 403 (the ones built on requirePrincipal). Cause traced: staff-only handlers call requireAuth → attachStaff → verifySession, which only knows staff sessions; an account token resolves to null and requireAuth writes 401 (src/http/middleware/requireAuth.mjs L107-115). requirePrincipal is the helper that distinguishes "no session" 401 from "wrong kind" 403 (src/http/middleware/requirePrincipal.mjs L86-93). Nothing leaked — every route denied — so this is a wrong status code, not an open gate; graded LOW, not HIGH. Side effect: the shell's data layer treats 401 as "signed out", so any future partner screen that touches one of these routes would look like a lost session, not a permission error. Not observed on the two partner screens (0 4xx).
- Evidence: route-probe.md "Failures — should be blocked but was not 403", route-probe.json blocked[].
