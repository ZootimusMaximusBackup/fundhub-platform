## What changed on 2026-09-04, after this was checked

Three people read this branch and re-ran the tests. They found the fix below **did not
work for the exact person it was written for**, and that four of my seven pictures were
pointing at the wrong thing. Both are fixed now. The corrections are here at the top so
nobody reads the old claims first.

**1. The sign-here form was still shown to some course buyers.** The rule is meant to be
"did you buy repair, or did you buy the funding package?" It was actually asking a second
question underneath: "does our credit engine grade you REPAIR_ONLY?" That grade comes off
a **real credit pull**, and it lands on anybody who gets pulled — course buyers included.
So a person who bought only a course, and whose credit file happened to grade REPAIR_ONLY,
was still handed the form and could still sign it. That is the original complaint,
unfixed. The grade is now gone from this decision completely, in both directions. The only
thing that opens the form is what the person paid for.

**One thing got narrower on purpose.** Somebody who has bought nothing at all, but whose
credit grade says REPAIR_ONLY, can no longer sign the form themselves in the portal. Staff
can still record their authorization on a call, and the do-it-yourself letter workflow
still runs off that grade exactly as before. Nothing else changed for them.

**2. The claim in the old text below that "a box can never be pointing at nothing" was
false.** Four of the seven "after" pictures had their red box drawn off the edge of the
picture and squashed onto the black bar at the bottom, so the caption described something
that was not in the shot. All fourteen pictures were retaken and every one was opened and
checked by eye. The picture-taker now fails on purpose if a box lands off the image.

**3. The database proof was hollow where it mattered most.** It claimed to check "a course
buyer whose stored grade says FULL_FUNDING". It wrote that grade into the wrong table, so
the grade the rule reads was empty for the whole test and the check passed without ever
being tried. It writes it where the rule actually reads it now, and there is a second leg
for the REPAIR_ONLY grade.

**4. The refusal on the server had no test at all.** The screen hiding the form was
tested; the server refusing the signature was not, and the server is the part that
actually stops anything. There are now eight tests for it. One of them was run against the
old code first and failed there, so it is not a test that would have passed anyway.

## Row 14, in plain words

Everybody who buys credit work has to sign one form first. It says we may prepare
dispute letters from their credit file. Without that signature we send nothing.

The earlier fix asked one question to decide who sees that form: **"is this a repair
customer?"** That answer is correct for repair. It is wrong for funding, because a
funding customer is not a repair customer — and the funding package we build for them
still contains dispute letters. So every funding customer had the form hidden from them.

Chris set the rule on 2026-09-03: *"It's only for repair and for the funding offer. If
they're getting deliverables, meaning e-products and courses, they don't need to sign
for shit."*

So the question is now **"did this person buy repair, or did they buy the funding
package?"** Both see the form. Nobody else does.

### One trap I stepped around

There is a second, easier-looking way to answer "is this a funding customer": look at
the grade our credit engine gives them after a credit pull. **That would have put the
form straight back in front of the course buyer this whole finding started with.** That
grade gets stamped on anyone who has a credit pull, including people who only bought a
course. So the code looks at **what they paid for**, never at the grade.

**I said that on 2026-09-03 and it was not true.** The code was still reading one grade —
REPAIR_ONLY — through a shared helper, and that is a real pull result, so course buyers
with a weak credit file went straight back through the hole. It is true as of 2026-09-04:
the grade is read nowhere in this decision, in either direction.

There is now a test that fails if anyone reads the grade here again, and a test for the
REPAIR_ONLY case specifically. That second one was run against the old code and **failed
there**, so it is proof rather than decoration.

### Two doors, not one

The form is hidden on the screen, **and** the server refuses the signature. Hiding
something is a courtesy; the refusal is the actual lock. Both use the same rule, from
the same one file, so they cannot drift apart.

The refusal now has its own tests — eight of them. It had none on 2026-09-03, which meant
the part I called "the actual lock" was the part nobody had checked.

If anything at all goes wrong — no answer from the database, an older version of the
site — the form stays **shut**. A course buyer wrongly asked to authorize credit
disputes is the bad outcome. A repair customer we have to send a link to by hand is the
harmless one.

## What I checked, and how hard

**In a browser** — `E2E_PORT=43219 npx playwright test w4b-portal-walk client-portal-ux` — **27 of 27 pass** (10 of them mine). Before the
fix, 9 of 10 passed: the failure was the funding buyer not being asked to sign.

**Against a real database** — `src/http/portal-summary-stage.pg.test.mjs`, **4 of 4
pass.** This one is the important one. It puts real rows in real tables, one at a time,
and asks the real page-data service what it now says:

* a credit pull lands → the page stops saying "before your call"
* a closer writes down how the call went → the page says the call happened
* an agreement is signed → the page says so, and does **not** claim they paid
* money posts → the page says they paid

Then it does the same with what the customer bought: nothing → no form. A course → still
no form, **even though their stored grade says FULL_FUNDING, and again when it says
REPAIR_ONLY**. The funding package → the form. Repair → the form.

The grade is now written onto the customer's own record, which is where the rule reads it.
On 2026-09-03 it was written into a different table, so the rule saw nothing and that
headline check passed without ever being tried. The test now refuses to run unless the
grade really is on the record first.

**Without a database** — `src/consent/dispute-consent.test.mjs`, 11 of 11, and
`src/http/consent-capture.test.mjs`, 64 of 64, eight of which are the server refusal.

**The whole test suite**, measured 2026-09-04 on this branch, on this laptop
(Postgres 16 on 127.0.0.1, a scratch database `fundhub_w4br` built from empty with all 238
migrations). The normal half: **8,616 tests, 8,613 pass, 0 failures, 3 skipped.** The
database half: **2,265 tests, 15 failures.** I extracted a clean copy of `main`, built it
a second scratch database the same way, and ran the same command: **2,261 tests, the same
15 failures, name for name — the lists match exactly.** Zero new failures. The 15 are
about the decline-autopsy upload flow and the repair letter generator, none of them near
this work.

**Lint** clean. **Journeys**: `npm run journeys` regenerates them and produced no
change, which is correct — no route moved and no route's permissions moved.

### A trap the next person will hit

**Two agents running browser tests at the same time will hand each other the wrong
files.** The browser-test config uses one fixed port (43117) and is set to re-use a
server that is already listening on it. When another workflow's copy of the repo has its
test server up, your tests silently load *their* copy of the page and dozens of tests
fail for no reason. It happened to me: 70 failures in one run, all of which pass alone.

The fix is one word on the command: `E2E_PORT=43219 npx playwright test …`. Everything
reported above was measured that way, on a port nobody else was on.

## Two honest gaps

**1. Nobody can assign an advisor.** Row 16 asked for the advisor's name to show. It
does. But **nothing anywhere in this system ever puts an advisor on a client's file.**
The place to store it exists and is never written to. So the name only appears when a
funding advisor happened to log a call on that file; for almost everyone the honest
answer is "Not assigned yet", and that is what they see.

Building an assignment step is not in the client journey document and I did not invent
one. It needs Chris to say who assigns, when, and from where.

**2. The database half of the suite has 15 old failures.** They are on `main` already
and none of them touch the portal. Listed by name in my hand-off so nobody has to
re-derive them.
