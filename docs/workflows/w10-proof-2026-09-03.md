## Row 8 (F42) — why nothing had ever been delivered

The live evidence in the walkthrough: four `analysis.completed` events in thirty
days, **zero deliverable documents ever, for any client**. Every gate inside C-06
was provably open for the client the walk used.

I could not reach the live run history from here, so I reproduced the whole path
locally instead of reading it. Running C-06's own `handle()` against a scratch
database with the sim's credit file behind it:

```
step resolve-client: ok
step check-product-path: ok
step tag-path-funding: ok
step deliver-funding-letters: ok
elapsed 2016ms
delivered: true, letterCount: 5, fundingLettersStored: 4
```

**The producing half works.** It builds five files and stores them. What never
happened is the invocation.

C-06 only runs when Inngest calls it, and the hand-off to Inngest is
`src/events/bus.mjs:49-53`:

```js
void inngest.send({ name, data: { ... } }).catch(() => {});
```

Fire and forget, with the rejection thrown away. If that send fails there is no
row, no log and no retry anywhere in the system — which is exactly what "the
event exists and the workflow never ran" looks like.

**The fix does not depend on Inngest at all.** `src/handlers/crs-deliverables.mjs`
listens for `analysis.completed` on the bus and calls C-06's own `handle()`. Same
code path, same gates, same idempotency key: `deliverFundingLettersOnce` stamps
the event id onto the client, and the bus hands the *same* events-row id to the
local dispatch and to Inngest, so whichever fires first delivers and the other
does nothing. This is the shape `src/handlers/diagnostic-soft-pull.mjs` already
uses, for this exact reason, on the credit pull itself.

A failure now leaves a durable row: the bus catches and dead-letters a throwing
handler.

**Proof** — `analysis.completed` emitted with `INNGEST_EVENT_KEY` deleted:

```
emit ok=true elapsed=2161ms
documents rows: 5
   bank_lender_match_list      | Bank and Lender Match List
   capital_readiness_summary   | Capital Readiness Summary
   credit_analysis_report      | Credit Analysis Report
   credit_optimization_roadmap | Credit Optimization Roadmap
   funding_snapshot            | Funding Snapshot
```

Two seconds. That runs inside the credit pull, which is already behind a bureau
call.

## Row 9 (F50) — the rendering, page by page

### The decision, and why

The reference set was produced by a WeasyPrint template
(`scripts/black-reports/fundhub_gen.py`, 1,614 lines, in this repository).
Netlify has no WeasyPrint, so production always falls through to the Node/pdf-lib
printer, and that printer was a skeleton.

> **The WeasyPrint printer was broken by this work and is fixed (Round 2
> repair).** The lender row grew from nine columns to eleven, and
> `fundhub_gen.py` unpacks each row POSITIONALLY into exactly nine names in three
> places, so it raised `ValueError`, `black-report-pdf.mjs` caught the non-zero
> exit and fell back to the Node printer, and no test or log ever said so. The
> earlier claim that "the Python template reads the old keys and they are all
> still there, so that path is unaffected" was wrong: the template reads those
> rows by position, not by key. All three unpacks now take `*_extra`. Proved by
> running the pre-fix and post-fix scripts against the same eleven-column
> client — `ValueError: too many values to unpack (expected 9, got 11)`, then
> five PDFs written. `src/underwrite/black-report-client.test.mjs` now asserts
> the arity and fails on the pre-fix line.

**I brought the Node printer up to the template rather than standing up a render
service.** A service is a new dependency, new infrastructure, a new secret and a
new failure mode; CLAUDE.md §8 says simplest thing that works and no new
dependencies without asking. The Node printer already runs everywhere the app
runs, needs nothing installed, and is the path production takes today.

### Two things NOT copied from the reference

1. **No projected score is invented.** The reference prints "700+ (projected)"
   and "690+". Nothing in this system computes a projected score — those strings
   are hand-typed sample values in the Python generator's `CLIENT` dictionary,
   alongside Jordan Sample's name. The after-optimization column instead carries
   the engine's projected **pre-approval**, which is real
   (`vendor/.../engine.js` re-runs the estimator over the fixed file), and the
   target states the findings actually name. Where a projected score would go,
   the document says "Set at your next pull".
2. **The booking link.** The reference itself prints
   `www.fundhubbookingurl.template` — a placeholder nobody replaced. The live
   documents print the real booking page.

### No new customer-facing claim is written

Every sentence in the two ranked sections is the vendor engine's own optimization
finding — `plainEnglishProblem`, `whyItMatters`, `whatToDoNext` — already written
at a 5th grade reading level by rules the engine ships
(`vendor/underwriteiq-full/api/lite/crs/optimization-findings.js`). This branch

## Row 11 (F43) — every account counted three times

A tri-merge report is three reports. An account that furnishes to all three
bureaus arrived three times and nothing merged them.

| | Before | Now | The walkthrough said it should be |
|---|---|---|---|
| Card rows | 9 | **3** | 3 |
| Car-loan rows | 3 | **1** | 1 |
| Total balance | $23,550 | **$7,850** | $7,850 |
| Total limit | $135,000 | **$45,000** | $45,000 |
| Paydown target | $13,500 | **$4,500** | $4,500 |
| Utilization | 17% | 17% | unaffected |

**The merge is in the display mapper, never in the engine.** Both sides of the
utilisation fraction triple together, so the engine's percentage — and the tier
and the pre-approval that follow from it — are correct as they stand. Collapsing
accounts upstream would silently move a funding number.

The key is creditor plus account identifier, the same pair the rest of the system
already matches on across bureaus. Two genuinely different accounts at one
creditor stay two rows, and that has its own test.

The vendor matcher decides "Business entity required" from
`businessSignals.available`, which is true only when a real **business credit
report** was passed to the engine. Fundhub buys none, so it is false for every

### WHO THIS FIX REACHES, AND WHO IT DOES NOT — read this before quoting the row above

**The sim academy client the walkthrough measured is still told to form an LLC,
and that is on purpose.** He has `businessAgeMonths: 72` in
`scripts/sim/push-credit.mjs`, but that number lands in
`clients.custom_fields.business_age_months`. It is not a `businesses` row. Under
the owner's F15 rule — no company row, no business — he does not have a company,
so his pack still reads "No business entity on file… Forming an LLC is fast" and
his roadmap still opens "Step 3: form your business entity."

Say it the way it is: **the LLC advice stops for a client with a `businesses`
row. It does not stop for a client who only has a number in a custom field.**
Anyone reading the row above as "F44 is closed for Sim Five" is reading it wrong.

Closing it for Sim Five means either writing him a `businesses` row or changing
what counts as having a company. The second is the owner's settled rule and this
lane does not touch it. Recorded as open, not quietly reconciled.

### A lender is only "open to you today" when every gate it states is met

Handing the matcher `available: true` off a company row exposed something the
matcher never checked. `vendor/.../lender-matrix.js:161-207` tests three things —
entity, months in business, score — and **never reads `minRevenue`**, though four
of its lenders state one: OnDeck $100,000, Bluevine $120,000, Kabbage $50,000,
Credibly $180,000 a year. Nothing in this product captures a client's business
revenue. So the first cut of this work told any client with a two-year-old
company that nine lenders were open to him today, four of which were not, with
their revenue floors nowhere on the page.

A revenue floor now moves the lender out of "available now" and into the
shortlist with the floor printed as what is still needed —
`$180,000/year in business revenue required (not on file)`. The lender is never
dropped and no number is zeroed: unknown revenue is shown as unknown.

## The funding estimate — unchanged, and how it is worked out

The lane required the estimate to follow the UnderwriteIQ rules exactly. It does,
because **no line of this branch touches it**. The four scoring-engine pins in
`src/underwrite/output-baseline.test.mjs` are byte-for-byte unchanged.

Stated accurately, from `vendor/underwriteiq-full/api/lite/crs/estimate-preapprovals.js`:

* **Personal card** — the largest revolving limit on the file × 5.5, floored at
  $5,000. Zero if there is no revolving anchor.
* **Personal loan** — the largest installment amount × 3.0, floored at $10,000.
  Zero if there is no installment anchor.
* **Three modifiers, multiplied together, and only three.** Outcome
  (PREMIUM_STACK and FULL_FUNDING 1.0, FUNDING_PLUS_REPAIR 0.6, everything else
  0), utilization band (excellent 1.0, good 0.9, moderate 0.75, high 0.6,
  critical 0.4, unknown 0.75), and thin file (0.6 when thin, else 1.0).
* **Business** — `bs.available === true` or it is **zero**. `available` is true
  only when a business credit report was passed to the engine. Then an age
  multiplier (under 12 months 0.5, under 24 months 1.0, 24+ months 2.0) over the
  card base, times the business utilization band and the outcome modifier, and
  hard-blocked to zero by any negative item, any UCC caution or any hard block.
* **Total combined** is personal card + personal loan + business.

There is **no revenue gate** in these rules and none was added. Bureau confidence,
inquiry pressure, AU dominance and the business overlay are all defined in that
file and all unused by v2 — they are prefixed with an underscore in the vendor
source. I neither used them nor removed them.

For the academy file: card base $25,000 × 5.5 = $137,500; loan base $28,000 × 3.0
= $84,000; outcome 1.0 × utilization 0.9 (17% is "good") × thin file 1.0; so
$123,750 + $75,600 = **$199,350**, business $0 because no business report exists.
Projected **$221,500**. Both figures are what the walkthrough recorded as
expected.
