# TASK 2 - Scheduled-run infrastructure

**The target:** a job that runs once a week without Chris, reads rule files out of the
repo, asks a model to write draft ad scripts, writes them back into the repo, and opens
a pull request.

## (a) Does any GitHub Actions workflow use a `schedule:` trigger?

**No.** There is exactly one workflow file, `.github/workflows/tests.yml`. Its triggers
are `push` (all branches), `pull_request`, and `workflow_dispatch`. I searched the whole
`.github` folder: one file, no `schedule:` key anywhere.

## (b) Can Actions write to the repo and open a pull request?

**No, on both counts, in two separate places.**

* The workflow file declares `permissions: contents: read`. That is read-only. There is
  no `pull-requests: write`.
* The repository default is also read-only. `gh api repos/:owner/:repo/actions/permissions/workflow`
  returns `{"default_workflow_permissions":"read","can_approve_pull_request_reviews":false}`.
* No step in the workflow uses `GITHUB_TOKEN` or any `secrets.` value at all. I grepped
  the whole `.github` folder and got zero hits.

So today an Action can read the code and run tests. It cannot commit, push, or open a
pull request.

## (c) Does Netlify have scheduled functions configured?

**Yes - five of them**, declared in `netlify.toml` rather than in code:
`commas-inbox-sweeper` (every minute), `creative-job-runner` (every 2 minutes),
`staff-message-sweeper` (every 5), `social-publish-sweeper` (every 5),
`hubstaff-poll-sweeper` (every 10). All five confirmed deployed by
`netlify functions:list`.

**But none of them helps here.** A Netlify function is a short web job. It cannot commit
to git or open a pull request, and it has no checkout of the repo to write into.

## (d) Does the Inngest clock actually fire today, and where does it run?

**Where it runs:** Inngest is a separate cloud service. It calls back into the Netlify
site at `https://fundhub.ai/api/inngest` to start each job. So the code runs inside a
Netlify function; the *clock* lives at Inngest.

**Does it fire:** everything I can check says the door is open.

* The route is wired ahead of the login check (`netlify/functions/api.mjs` line 1037).

  a 404 and not a login page.
* `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY` are both set in the Netlify production
  environment.
* 11 cron jobs are registered.

**UNVERIFIED:** I could not see the Inngest dashboard, so I cannot show you a run that
happened. Everything above is "the wiring is right", not "it ran at 7 a.m. today".

**Same limitation as (c):** an Inngest job runs inside a Netlify function. It has no git

## What is missing

Most blocking first.

1. **Nothing in this repo runs on a weekly clock outside Netlify.** No GitHub Actions
   `schedule:` trigger exists. That is the one piece the target needs and the only place
   it can live, because it is the only runner that gets a git checkout.
2. **GitHub Actions cannot write to the repo.** The workflow says `contents: read` and
   the repository default is also `read`. Both have to change before any job can commit
   a draft ad script.
3. **GitHub Actions cannot open a pull request.** No `pull-requests: write` permission,
   and `can_approve_pull_request_reviews` is false at the repo level.
4. **No model key is available to GitHub Actions.** `ANTHROPIC_API_KEY` and
   `OPENAI_API_KEY` exist on Netlify and are named in `.env.example`, but Netlify
   environment variables are not visible to GitHub. **Proven:** `gh secret list` and
   `gh variable list` both return **completely empty** - this repository has zero secrets
   and zero variables configured. So every key a model job needs would have to be added
   as a GitHub repository secret first. Full output in section 2(h).
5. **No agent or model package is installed.** There is no SDK and no Claude CLI in
   `package.json`. A job would either call the model with plain `fetch` the way
   `src/agents/model.mjs` already does, or a package would have to be added - and
   CLAUDE.md section 8 says no new dependency without asking.
6. **Ad tooling exists, but nothing in it writes an ad script on its own.** An earlier
   draft of this page said flatly "there is no ad-script generator to schedule" without
   opening `scripts/ads/` or `docs/ads/build/`. Both exist and both hold runnable code.
   What is actually there: `scripts/ads/check-registry-titles.mjs` (2026-09-03) checks
   that every ad has a name and **deliberately refuses to invent one**;
   `docs/ads/build/build-sheet.py` (2026-09-03) reformats concepts that already exist,
   and cannot even do that today because the three input files it loads are not in the
   folder; and the flywheel `copy.js` stage runner is written for a person sitting in an
   agent session, with no command-line entry point. `docs/ads/scripts/` really does hold
   only a README, and that README says the 83 real ad scripts from 2026-09-02 are still
   sitting in a Claude chat rather than in the repo. **The piece the target job needs -
   something that turns the rule files into new draft scripts with nobody watching - has
   to be written.** Full file-by-file detail in section 2(g).
7. **Netlify and Inngest cannot do this job at all.** Both run inside a serverless
   function with no git checkout. They can call a model; they cannot commit a file or
   open a pull request. Worth stating so nobody spends a day trying.
8. **Nothing checks the ad rule files are current.** `npm run flywheel:status` is the
   staleness gate and it is human-typed only. A weekly job would happily build on stale
   input unless it calls that first.
9. **The live database is eleven migrations ahead of the checked-in list.**
   `curl -s https://fundhub.ai/api/health` returns `"migrations":262,"expected":251`.
   `pending` is 0, so nothing is waiting to be applied - but the applied count and the
   expected count do not agree, and the applied count has moved (an earlier reading said
   258). I did not trace why, so I am not guessing a cause. Someone should look.

   *(Item 9 in an earlier draft said three nurture sequences were "dead and nothing
   noticed". That was wrong - they were retired on purpose on 2026-08-22, with the
   decision written in the code and pinned by three tests. It is not a missing thing, so
   it has been taken off this list. See section 1i.)*
10. **The daily pulse cron needs a manual change when the clocks go back.** Its own file
    says `0 13 * * *` must become `0 14 * * *` after the fall-back, or it fires at 6 a.m.
    Denver. Nothing enforces that.
