## 4. Hours in chat on marketing

**This whole section is an estimate. Read the method before you read the number.**

### Method, in one line

I read every saved chat transcript on this machine for this project, took the time from its first message to its last, capped any one chat at 4 hours, and sorted each chat into marketing or coding by counting whole marketing words against whole coding words.

### First problem: the session tool gives no start time

`mcp__ccd_session_mgmt__list_sessions` with archived sessions included returned **39 sessions**. Each one has `lastActivityAt` and nothing else time-wise. There is no first-message time, so there is no length. **The tool alone cannot produce hours.**

So I fell back to the raw transcript files on disk, which do carry a timestamp on every message:

```
~/.claude/projects/-Users-zootimusmaximus-fundhub-platform/*.jsonl
```

**105 transcript files.** These do have real start and end times.

**Declaring the swap.** The task named `mcp__ccd_session_mgmt__search_session_transcripts` as a tool to use for sorting sessions into marketing or coding. **I used the transcript files instead, and this line is me saying so out loud rather than leaving the substitution silent.**

I did then run the search tool as a cross-check. Searching `VSL` returned 13 sessions; searching `ad script` returned 3. Both are much lower than the 20 marketing files the transcript scan found, and the reason is simple: **the search tool returns one hit per session and only shows a snippet.** It tells you *which* chat mentioned something. It cannot tell you *how much* of that chat was about it, and it gives no times at all. For counting hours the raw files are the better instrument. The cross-check did agree on direction - every session the search flagged for `VSL` or `ad script` was one the file scan had already put in marketing or mixed.

### Reconciling 39 sessions against 105 files

These are two different inventories and they do not line up one-to-one.

- **None of the 105 filenames match any of the 39 session ids.** The session tool lists sessions the desktop app knows about. The `.jsonl` folder holds every conversation run against this project, including command-line runs and background agents the app never listed.
- **Resumes are not inflating the count.** The worry was that one long conversation resumed several times would be counted as several sessions. I tested it: of 55,416 message ids across all 105 files, only 228 appear in more than one file, and merging every file that shares a message id gives **104 separate conversations out of 105 files.** Exactly one conversation spans two files. So the 20 / 72 / 11 split below is 104 real conversations, not one conversation counted twenty times.

The 39-versus-105 gap is a **coverage** gap, not a double-counting one. Both are floors.

### Second problem: only 12 days are saved

The transcripts run from 2026-08-02 to 2026-09-06, and only 12 separate days have any file at all:

`08-02, 08-17, 08-18, 08-19, 08-27, 08-28, 08-29, 08-31, 09-03, 09-04, 09-05, 09-06`

Meanwhile git shows commits on **40 separate days** in the same window. So the chat history is missing at least 28 working days. The first five weeks of the window have one single transcript in them.

**The hours below cover 12 days out of 60. They are a floor, not a total.** Anything that says "per week" here is really "per week if the other 48 days were empty," and they were not.

### Third problem: word matching is fragile

My first pass matched the word `ad ` and `ads` as plain text. That also matched **read**, **threads**, **uploads** and **leads**. It called 41 sessions marketing. Once I switched to whole-word matching, the same 105 files gave **19** marketing sessions.

A number that moves from 41 to 19 on a spelling detail is not a precise number. The word `script` is also genuinely ambiguous here, because this repo has a `scripts/` code folder. Treat the split below as rough.

Marketing words counted: ad, ads, script, scripts, hook, hooks, VSL, creative, creatives, funnel, funnels, copy, avatar, avatars, offer, offers, sorting hat.
Coding words counted: test, tests, migration, migrations, endpoint, endpoints, deploy, deployed, schema, pull request, lint.

Split rule: 60% or more marketing words is MARKETING, 40% or less is CODING, in between is MIXED.

Result over 105 transcripts: **19 marketing, 70 coding, 12 mixed, 4 with no matching words at all.**

A re-run of the same rule gave **20 marketing, 72 coding, 11 mixed, 2 with no matching words.** The two runs differ by one or two files in each bucket because of small differences in how much of each message the scan reads. **That drift is itself the finding: this split is accurate to about plus or minus two files, and should never be quoted to the exact chat.**

### Fourth problem: the 4-hour cap is doing almost all the work

This was buried in the method line and it should not have been. **It changes the answer more than anything else in this section.**

Every chat is capped at 4 hours before it is added up. Here is what that cap throws away:

| | Total across 105 files |
|---|---|
| **Uncapped** - first message to last, as recorded | **817.3 hours** |
| **Capped at 4 hours a chat** - the number used below | **207.4 hours** |

**Three quarters of the recorded span is thrown away by the cap.** So the headline hours describe the cap at least as much as they describe Chris.

**Why the cap is still the right call.** 34 of the 105 files run longer than 4 hours from first message to last, and the longest five are 53.7, 54.9, 57.5, 68.8 and **72.0 hours**. A 72-hour chat is not 72 hours of work - it is a window left open across three days. Adding those raw would be nonsense.

**Why you should not trust either number too far.** 817 hours is clearly too high. 207 is a guess with a round number in it. Nobody measured how long Chris was actually at the keyboard. If the real cap should have been 2 hours or 6, the answer moves a lot. **Treat the hours as a rough shape, and treat the marketing-versus-coding ratio as the more reliable part of this section** - the ratio survives the cap far better than the total does.

### Fifth problem: many chats run at the same time

Chris runs several agents in parallel. If you just add up how long each chat lasted, you count the same hour many times over. Adding them gives 207 hours. Merging the overlapping ones gives 86 hours. The second is closer to real time in front of the screen.

I report both so you can see the gap.

That is the real shape of the problem. On three days out of four, Chris was switching between writing ads and shipping code. Neither gets a clean run at the day.

Note on how I counted that: a MIXED chat counts as both kinds, because by definition it was both.
