# Creative Factory - the data underneath, and what is empty

Read-only lane. I read the SQL files and the code. I did not touch a database.

## The short answer

The tables are built well. The pipes into them are mostly missing.

Three things stop Chris getting finished ad creative out of the screen:

1. **The screen has no way to pick a partner.** This is the first wall and it
   comes before all the others. There is no partner list on the page and no
   place that hands the page one. The only way the screen learns which partner
   it is looking at is if the partner's long id code is already typed into the
   web address, like `...creative-factory.html?partner_id=<long code>`. If Chris
   just opens Creative Factory from a menu or a bookmark, every panel is empty
   and every button is greyed out, and nothing on the page says why.
2. **No vendor is switched on.** The table that says "use this ad-making service"
   ships with zero rows, and no seed file, no migration, and no button anywhere in
   the app puts a row in it. Someone has to type SQL by hand.
3. **Nothing in the app can make a brand kit.** Not one line of code writes to the
   brand kit tables. The screen even says "Brand kits are read-only here."
   So the brand kit list is always empty, forever, on every account.

There is a fourth, quieter one: the every-two-minutes robot that is supposed to
pick up queued jobs picks up nothing. Details in Task 3.

**Not a blocker, though an earlier draft of this note said it was:** the picture
and video services ship with a stand-in web address in the code. That is a
factory setting, not a dead end. The same row that switches a vendor on is the
row that carries its real address. See "the vendors are not real yet" below.

## TASK 1. The five tables, in plain English

### brand_kits

Holds one partner's look: name, the web address it came from, colours, fonts,
logo, tone of voice, and a list of products. This is the recipe a generated ad is
supposed to follow.

Must be filled in, no fallback: `org_id`, `partner_id`, `name`.
Everything else has a default or may be left blank.

`status` allows exactly: `'draft'`, `'active'`, `'archived'`. Default `'draft'`.

Two names cannot repeat inside one partner. A blank name is rejected.

### brand_kit_sources

The raw copy of each web page we fetched when building a brand kit. Kept so a
better reader can re-read it later without going back to the partner's site.

Must be filled in: `org_id`, `partner_id`, `brand_kit_id`, `source_url`.

No status column. Rows here can never be deleted - a database rule blocks it.

### creative_assets

One finished thing: a picture, a video, or a block of words.

Must be filled in, no fallback: `org_id`, `partner_id`, `kind`, `format`,
`ai_generated`. That last one is deliberate. There is no default, so a caller
that forgets to say "a machine made this" gets an error instead of being quietly
recorded as human-made.

| Column | Allowed values |
|---|---|
| `kind` | `'static'`, `'video'`, `'copy'` |
| `format` | `'1x1'`, `'4x5'`, `'9x16'`, `'16x9'` |
| `compliance_state` | `'pending'`, `'passed'`, `'blocked'`, `'approved'` (default `'pending'`) |

Extra rules the database itself enforces: a blocked asset must list at least one
reason; only a video may carry a length; a file path must start with
`partners/<that partner's id>/`; anything showing a fake person must also be
marked machine-made. Rows can never be deleted, only archived.

### generation_jobs

One request to make creative. Holds what was asked for, which vendor ran it, what
it cost us, and what went wrong.

Must be filled in, no fallback: `org_id`, `partner_id`, `idempotency_key`.
That last one is the "name this batch" box on the screen. It stops a double-click
paying twice.

`status` allows exactly: `'queued'`, `'running'`, `'succeeded'`, `'failed'`.
Default `'queued'`.

A failed job must carry a reason. The database refuses a failure with no
explanation.

Migration 241 added `requested_by_kind`, which allows `'staff'`, `'partner'`, or
nothing at all. Nothing at all is legal and means "a robot asked, nobody signed in."

241 also added a rule the database enforces called
`generation_jobs_requester_ck`. In plain words: **the row has to name at most one
asker, and it has to be the kind of asker it says it is.**

- Says "staff": the employee's id must be filled in, and the partner-account box
  must be empty.
- Says "partner": the partner account's id must be filled in, and the employee
  box must be empty.
- Says nothing: both boxes must be empty.

Any other mix is refused. So a job cannot be recorded as asked for by an
employee and a partner at the same time, and it cannot claim an asker it does not
name.

### generation_job_assets

A plain join list: this job made that asset. Must be filled in: `org_id`,
`partner_id`, `job_id`, `asset_id`. No status column.

## TASK 2. What ships empty on purpose, and what it blocks

### THE BIG ONE: `creative_providers` - zero rows, nothing fills it

**What it is.** The list of ad-making vendors. One row means "for pictures, use
this service."

**Is it really empty?** Yes. I checked every one of the 22 files in `db/seed/`.
Not one of them mentions the word "creative" at all. No migration inserts a row
either. The migration that creates it says so in its own header: "NOT SEEDED WITH
AN ACTIVE ROW."

**What Chris would see** (assuming he has already got a partner id into the web
address - see step 1 of the walkthrough, because without that he never reaches
this point). He types what he wants, names the
batch, presses **Enqueue generation**. The screen says the job was saved, and
then says plainly: *"it cannot run yet: no ad-making service is switched on for
this account."* If he then presses **Run queued jobs now**, the job is marked
failed and nothing is made. Retrying will never help - the code treats "no vendor"
as permanent, not as a hiccup.

**Who fills it.** Nobody, through any screen. There is no admin page for this. I
searched the whole `public/` folder: the only mentions of `creative_providers` are
in code comments. It has to be typed straight into the database by hand, one row
per kind of thing you want to make.

**One honest note in the other direction:** the screen does not lie about this. It
tells the reader, in plain words, that nothing can be made until a vendor is on.

### `ad_platform_category_map` - was empty, is now filled

Migration 046 left this blank on purpose and blocked all Meta ad launches.
Migration 052 filled it in with `CREDIT` for all three offer types. So this one is
no longer a blocker, but the value is marked "confirm against your Meta API
version before the first launch."

### `creative_billing_rates` - has numbers, but nobody has agreed them

Two rows. Migration 050 created them with no number, which made billing refuse to
run. Migration 052 set them: 100% markup on generation cost, 10% of managed ad
spend. Both are labelled PLACEHOLDER and both are still reported as
"AWAITING SIGN-OFF" until a human stamps them. Billing works; the numbers are
guesses. Chris is the person who decides them.

### `optimization_rules` - two rules shipped switched off on purpose

These are the automatic rules that watch an ad campaign and act on it. Seven
shipped. Five came with numbers. Three of them were deliberately left blank in
migration 048, and the database has a rule that says **a rule with a blank
setting is not allowed to be switched on**. So they could not run at all.

The two that shipped fully off and flagged:

- **`kill_no_conversions`** - the money kill switch. "Stop an ad once it has
  spent this much and made zero sales." The "this much" was left blank on
  purpose. **What stops:** nothing pauses an ad that is burning money and
  selling nothing.
- **`spend_tier_refresh`** - how often to swap in fresh creative as daily spend
  goes up. The list of spend levels was left empty on purpose. **What stops:**
  the refresh cadence never tightens; tired ads keep running.

A third, **`roas_primary`**, shipped with its "target return" blank. That one is
the policy that protects a profitable campaign from the other rules cutting its
budget.

**Where it stands now.** Migration 052 filled in all three: $500 spend floor for
the kill switch, a four-step spend/refresh table, and a break-even target of 1.0.
All three are labelled "derived, not observed - tune against your own numbers."
So this is the same "was empty, now defaulted" category as
`ad_platform_category_map` above, and it belongs on this list for the same
reason.

**Who sets the real numbers.** Chris. They are one `UPDATE` each in the database,
and there is no screen for them. 052 writes the exact command in a comment next
to each one.

### `partner_module_settings` - no row means the whole thing is off

Not really a config table, but it behaves like one. If a partner has no row here,
`marketing_suite_enabled` reads as false and the Generate button returns
*"The owner has not turned this on for this partner."*

The switch exists and works - but it lives on the **Brand Studio** screen, not on
Creative Factory. So the order is: Brand Studio, turn the partner on, then come
back. Nothing on the Creative Factory screen tells him where that switch is.

### The "settings the engine ships with" table on the screen is hardcoded

The panel at the bottom of Creative Factory that lists these gaps is fixed text
written into the page. Its own caption admits it: "These are not read back from
the running system." The live version of that list exists in the database as
`v_creative_config_gaps`, and no endpoint serves it. So if someone fixes a gap,
that panel will still say it is broken.

That live list has **four** parts, and all four are covered above:
`ad_platform_category_map`, `creative_providers`, the two
`creative_billing_rates`, and the three `optimization_rules`.

## TASK 3. Who writes to these tables

I grepped the whole repo for inserts and updates into all five.

| Table | Written by real app code? |
|---|---|
| `brand_kits` | **No.** Tests only. |
| `brand_kit_sources` | **No.** Tests only. |
| `creative_assets` | Yes - `src/creative/generate.mjs` |
| `generation_jobs` | Yes - `src/creative/generate.mjs` |
| `generation_job_assets` | Yes - `src/creative/generate.mjs` |

### The two tables nothing writes

`brand_kits` and `brand_kit_sources` are written **only** by test files. There is
no site scraper, no "create brand kit" form, no import script. The single mention
of scraping in the whole creative area says FundHub deliberately does not scrape
and buys data from vendors instead - and that is a different module.

**What Chris sees:** the Brand kits panel is always empty, the brand kit dropdown
on the library filter is always empty, and the tile that says "ACTIVE BRAND KITS"
always reads 0. Every ad he generates is made with no brand recipe attached.

### The one writer, and how it is reached

`src/creative/generate.mjs` does everything: creates the job row, stores each
asset, links them, then runs the compliance check.

It is reached three ways:

- **POST /api/creative/generate** - the Enqueue button. Creates the job row only.
- **POST /api/creative/run, with a partner named** - the "Run queued jobs now"
  button. This one works, because the screen always sends a partner id.
- **POST /api/creative/run, with `all=1` instead of a partner** - employees only.
  No button sends this; it is reachable only by calling the address directly.
  **It has the same fault as the robot below.** It runs the exact same
  "which partners have queued jobs?" question on the same blind connection, so it
  finds nobody and reports that it ran nothing. The lane's first draft called this
  endpoint "works" without noticing it has two modes.
- **The every-two-minutes robot** (`netlify/functions/creative-job-runner.mjs`).
  Finds nothing. See below.

### The robot that never finds a job

`src/creative/runner.mjs` starts by asking "which partners have queued jobs?" It
asks that question on a plain connection, without first telling the database who
it is acting as. Every one of these five tables has a security rule that hides all
rows from a caller who has not said who they are. So that first question returns
zero partners, and the robot stops before it claims anything.

The system's own comments say this pattern is a known trap: an unset caller
"sees an empty table, never someone else's rows. That is the whole design."

**What Chris sees:** the message after enqueueing says the job "is picked up
within a few minutes." It is not. Jobs sit in the queue until somebody presses
"Run queued jobs now" by hand.

**CONFIRMED.** Not a guess, and no live check is needed. The repo already proves
both halves of it, and both proofs run on every push.

**Proof one - the blind question really does come back empty.**
`src/creative/generate.pg.test.mjs` line 106 is a test called *"an unscoped read
returns nothing rather than everything."* It runs
`SELECT id FROM generation_jobs` with nobody named, on the app's own limited
login, and it insists the answer is nothing. That is the same question the robot
asks. `src/compliance/invariants.pg.test.mjs` line 116 does the same thing across
every table in the module at once - its own name is "THE LEAK TEST."

**Proof two - the tests use the same kind of login the live app uses.**
`src/testing/rls-pool.mjs` exists only for this. Its opening note explains that
the database's owner account walks past every one of these rules, so an isolation
test run as the owner proves nothing, and these tests therefore run as the
limited `fundhub_app` login instead.

**Proof three - the live app cannot be running as a super-user.**
`src/security/superuser-guard.test.mjs` checks the app's real database login and
fails the Netlify build if it carries super-user power. It is deliberately not
named `.pg.test.mjs` so it can never quietly skip itself. So the one thing that
could have made this finding wrong is blocked at deploy time.

**What is still true:** nothing calls `runDue` in any test. The behaviour is
pinned; the function that depends on it is not. That is why it went unnoticed,
and a test on `runDue` itself is the thing worth adding.

## TASK 4. Later changes to these five tables

Only one migration ever changes them after 045.

**`241_generation_jobs_requested_by.sql`** (landed 2026-08-19 by its own note).

It adds three columns to `generation_jobs`: `requested_by_kind`,
`requested_by_staff_id`, `requested_by_account_id`.

It also adds a new database rule, `generation_jobs_requester_ck`, which is not
just a column change - it is a new agreement every job row has to keep. A row may
name **at most one** asker, and it must be the kind of asker it claims: "staff"
means the employee box is filled and the partner box is empty, "partner" is the
reverse, and naming no kind means both boxes are empty. Anything else is refused
outright. Full wording in Task 1 under `generation_jobs`.

**The bug it fixed, in Chris's terms:** when an employee pressed Generate, the
screen showed an error every time. When a partner pressed it, it worked. The cause
was that the original column pointed at the customer list, and employees are not
in the customer list. So every employee request was rejected by the database. This
is exactly the kind of thing that makes a feature "look done" and fail for the
owner personally.

The old `requested_by` column was left in place, empty, and is never written to
again. That follows the rule in `CLAUDE.md` §12 - you supersede a migration, you
never edit it.

**Everything else only points at these tables, it does not change them:**

- 046 - the ad-object list points at `creative_assets`
- 047 - the compliance rules point at `creative_assets` for the disclosure image
- 049 - social posts point at `creative_assets`
- 050 - billing events point at `generation_jobs`

No other migration adds, drops, or alters a column on any of the five.

## TASK 5. Row level security - who can see whose rows

All five are protected, and in the strongest form available.

Migration 045 runs one helper over all five names at once. That helper does three
things per table: switches the rule on, forces it to apply even to the database's
own owner account, and installs a single policy covering reads, inserts, updates
and deletes together.

The policy is: you see a row if it belongs to the partner you said you were, or
if you said you were FundHub staff. Say nothing, see nothing.

| Table | Protected | Forced | Matches the rest of the repo |
|---|---|---|---|
| brand_kits | yes | yes | yes |
| brand_kit_sources | yes | yes | yes |
| creative_assets | yes | yes | yes |
| generation_jobs | yes | yes | yes |
| generation_job_assets | yes | yes | yes |

It does match how the rest of the code scopes partners. All five names also appear
in the app-side allow-list in `src/partners/scope.mjs`, which is the second lock,
and in the test list in `src/compliance/invariants.pg.test.mjs`, which fails if any
of them loses its policy or stops forcing it.

Two things worth saying out loud:

- The strictness is real, and it is what breaks the robot in Task 3. Same rule,
  two different outcomes.
- Nothing here is weaker than the rest of the repo. If anything the creative
  module is the strictest part of it - 045's header says it is where this style of
  protection was introduced.

## Extra finding: the vendors are not chosen yet

Not asked for, but it decides whether any of this can work at all.

**CORRECTION to the first draft of this note.** It said the picture and video
work "would be sending real requests to an address that does not exist." That
was wrong, and it was wrong because I read the four modules and did not read the
piece of code that feeds them.

Here is what is actually true. Each module asks for its web address like this:
*"use the address on the vendor's row; if that row leaves it blank, use this
one."* The stand-in address is the second half of that sentence - a factory
setting, not a hard-wired dead end. The vendor's row is exactly the thing that
carries the real address: migration 048 describes that box, in its own words, as
"Endpoint, model, default avatar, per-unit cost." And `providers/index.mjs` is
the code that reads that box off the row and hands it to the module.

So the honest version is: **the address ships as a stand-in, and it gets set in
the same row that switches the vendor on.** One job, not two. This is not a
separate blocker and should not be counted as one.

The counts in the first draft were wrong too. **Four** modules carry a stand-in
address, not three, across **four** different made-up domains, not two:

| Module | Stand-in address it ships with |
|---|---|
| pictures (`static`) | `api.example-image-provider.com` |
| AI-actor video (`ugc-video`) | `api.example-ugc-provider.com` |
| product video (`product-video`) | `api.example-product-video.com` |
| resizing (`resize`) | `api.example-resize.com` |

The first draft left `resize` out entirely.

**What IS still true and does still matter:** four of the five modules carry a
warning at the top saying their message shape has never been tested against a
real vendor account. So the address is a filled-in box; whether the message we
send matches what a real vendor expects is untested. That is a first-run risk,
not a blocker.

Only the **copy** module (writing words) talks to a service that is already
chosen and real, and its key `ANTHROPIC_API_KEY` is present in the local `.env`.

The four picture and video modules each want their own key, and none of the four
names is in the local `.env`: `CREATIVE_STATIC_API_KEY`, `CREATIVE_UGC_API_KEY`,
`CREATIVE_PRODUCT_VIDEO_API_KEY`, `CREATIVE_RESIZE_API_KEY`.

**UNVERIFIED:** whether those four keys are set on the live site. I cannot check -
the Netlify API is blocked from here (CLAUDE.md §11). **What would settle it:**
`netlify env:list --context production --plain` and look for the four names. Names
only; never print a value.

**So the honest position on pictures:** the address is not the problem. The
problem is that no picture or video vendor has been chosen, signed up for, or
paid for. Pick one, put its address and its key in, and the machine has a chance
of working on the first try - with the caveat above that the first try is the
first real test of the message shape. Words are further along, because the vendor
for words is already picked and its key is on the machine.

## What Chris would actually do, step by step, if he opened it now

1. **Open Creative Factory. It does not ask him to pick a partner - and this is
   where he stops.** There is no partner list on the page and nothing that hands
   the page one. The page only knows a partner if the partner's long id code is
   already in the web address, after `?partner_id=`. Opening the screen any
   normal way means: every panel shows its empty state, no request is even sent,
   and the buttons are greyed out. Nothing on the page explains this. To get past
   step 1 he has to find a partner's id code and paste it into the address bar by
   hand. (An earlier draft of this note said the screen "asks him to pick a
   partner." It does not. That was the biggest thing this walkthrough got wrong,
   because it turned the first wall into a friendly step.)
2. Say he gets a partner id in. If that partner was never switched on in Brand
   Studio, **Enqueue generation** answers "the owner has not turned this on for
   this partner."
3. If it was switched on, the job saves, and the screen tells him honestly that no
   ad-making service is on.
4. **Run queued jobs now** marks the job failed. The failure reason on screen is
   "No ad-making service is switched on for this account."
5. The library stays empty. The brand kits panel stays empty and always will.

Nothing about this is broken code. It is a finished machine with no fuel line -
and no handle on the door.
