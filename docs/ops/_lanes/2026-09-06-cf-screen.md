# Creative Factory - what the screen actually lets you do

Read of `public/app/creative-factory.html` (2,484 lines, all of it), plus the
seven endpoints it calls, the route map, the database tables behind it, and
`shell.js`. Written for Chris. No code in the findings.

Corrected 2026-09-06 after a second pass. Six things in the first version were
wrong or missing and are fixed below. The biggest: the first version said there
is no column for a picture. There is. See Task 2, step 7.

---

## The short answer

The screen is not a shell. It is a real, careful, well-built screen. Almost
every control on it calls a real endpoint that really exists.

But it cannot give you an ad. Three separate things stop it, and any one of
them is enough on its own:

1. **You cannot click your way to the screen.** The whole **Marketing** heading
   is hidden from the menu, so Creative Factory, Campaigns, Social Studio and
   Content are all invisible together. Three separate rules do the hiding, not
   two. The only way in is typing the address.
2. **Nothing is switched on to make ads.** The system needs one row saying
   which company makes the pictures. That row has never been created, in any
   file, ever. Four of the five ad-makers also point at made-up web addresses.
3. **Even if both of those were fixed, you still get nothing you can look at.**
   The words of a written ad are thrown away. The picture's address is kept -
   but nothing ever uploads a file to that address, so the address points at
   nothing. And a one-line bug means the screen is never even told whether an
   address exists, so the tile would say "no preview available" either way.

Point 3 is the one that matters, and it is now three smaller problems instead
of one hole in the design. Two of them are a day of work. One of them is a
single line.

## TASK 1 - every control, and what is really behind it

Counted from the file: 3 typing boxes, 8 dropdowns, 29 button tags. Ten of the
buttons are the shared menu frame (the collapse arrow and the nine section
headings) and are not part of this screen. Everything else is listed below by
name. Nothing is grouped into a category.

### WORKS - calls a real, routed, working endpoint

| On screen | What it does | What it calls |
|---|---|---|
| **Partner** dropdown | Picks whose work you see | `/api/read/partners`, then re-reads all four panels |
| **Enqueue generation** button | Adds a job to the queue | `POST /api/creative/generate` |
| **Run queued jobs now** button | Starts the queue now | `POST /api/creative/run` |
| **Approve** button | Approves the picked creative | `POST /api/creative/actions` |
| **Reject** button | Rejects the picked creative | `POST /api/creative/actions` |
| **Archive** button | Archives the picked creative | `POST /api/creative/actions` |
| **Approve this brand** button (one per review row) | Approves a partner's brand | `POST /api/brand/review` |
| **Send it back** button (one per review row) | Refuses a partner's brand, with a reason | `POST /api/brand/review` |

Plus the four reads that fill the page, all real and all routed:
`/api/creative/jobs`, `/api/creative/library`, `/api/creative/brand-kits`,
`/api/creative/approvals`. The allowance card reads
`/api/partner-marketing/usage`.

### DEAD - looks like a control, does nothing

| On screen | Why it is dead |
|---|---|
| The five tiles under **"What each job state means"** | They are built as buttons. They have a hand pointer and they light up when you hover. Nothing is attached to them. Nothing happens when you click. |
| **Kind = "resize"** in the Generate box | A resize needs you to say which existing ad to reshape. This screen never asks and never sends it. You cannot pick a parent anywhere on the page. Today a resize job would not even get that far: it stops earlier, at "no ad-making service is switched on", because no such row exists. If that were fixed, the next stop is the resize code refusing with *"resize requires a parentAsset with an id"*. (The first version of this report quoted that message wrong, as "resize requires a parent asset".) |

Those two are the whole dead list. Every control that carries a data tag -
every filter chip, every tile, every per-row button - was checked against the
click handlers, and every one has a listener. The legend tiles are the only
exception.

Worth saying plainly: the page's own notes show somebody already found this
problem on the five big number tiles at the top and fixed them by turning them
into plain boxes. The legend tiles were missed.

### DEAD BY OMISSION - a control that should exist and does not

- **You cannot choose the shape.** The library has a filter for four shapes
  (1x1, 4x5, 9x16, 16x9) but the Generate box always asks for 1x1 and nothing
  else. Three of the four filter chips can never match anything you made here.
- **You cannot ask for more than one version.** Every job asks for exactly one.
- **You cannot pick a brand kit for a job.** The job is always made with no
  brand kit, so no colours, no fonts, no tone of voice.
- **You cannot pick a parent for a resize.** See the dead list above.
- **You cannot get the ad out.** No download, no copy button, no preview, no
  link. See Task 3.

### SETTLED - was UNVERIFIED, now answered from the code

- **The Partner dropdown, on a partner sign-in, always has exactly one entry
  and can never be empty.** Creative Factory is handed to the partner role in
  `shell.js`. The partners list lets a partner in and pins them to their own
  row, so a signed-in partner always sees themselves and only themselves. No
  browser needed.

### UNVERIFIED

- **Does the Partner dropdown have anybody in it on YOUR sign-in?** The owner
  and staff case is different from the partner case above - staff get the list
  filtered to their own company, and if the company has no partners the
  dropdown is empty and the whole screen is dead in one step. Settled by: open
  the screen signed in as owner and look at the dropdown.
- **Is the writing allowance switched on for any partner?** The default is off,
  and only Brand Studio can turn it on. Settled by: open the screen and read
  the "On?" box in the allowance card.

## TASK 2 - the walk, as Chris would do it

**1. He tries to find it, and there is nothing to find.** He opens the CRM and
looks down the left menu. **There is no Marketing heading at all.** The whole
section is hidden, so Campaigns, Social Studio, Content and Creative Factory
all vanish together - he does not see a Marketing group with things missing
from it, he sees no Marketing group.

Three separate rules do this, and the first version of this report only found
two:

- the hidden list in the menu code (`shell.js`),
- the hidden list of addresses in the menu stylesheet,
- and a third rule in the same stylesheet that hides the entire Marketing
  section outright, whatever is inside it.

That third rule is the one that actually decides it. Every other screen in the
app carries the same hidden menu, so there is no link to Creative Factory from
anywhere. **He has to type the address.**

**2. He types the address and the page is blank.** Not blank-white - the boxes
and headings are all there, but the five big numbers, the jobs table, the
library, the review queue and the brand kits are all completely empty. No
"loading", no grey placeholder bars, no message. This lasts until two calls
come back. On a slow connection it reads as broken. Only the allowance box
says "Loading the allowance...".

**3. The page fills in.** Five numbers across the top. Then a box asking which
partner. Then a box about a monthly writing allowance measured in "small pieces
of text". Then, third card down, the Generate box.

**4. He looks for the Generate button and it is greyed out.** Beside it, in
small grey type: *"The owner has not turned this on for this partner."*
That is him. He is the owner. The screen does not tell him where to go and
turn it on, and there is no link. The switch lives on a different screen -
Brand Studio - which is also hidden from the menu.

**This is where a person gets stuck.** The exact control is the
**Enqueue generation** button. It is off, and the sentence explaining why does
not say what to do about it.

**5. If he gets past that**, he types a description, types a batch name,
presses Enqueue. He gets back: *"Saved to the queue, but it cannot run yet: no
ad-making service is switched on for this account. The next try will be
recorded as a failure and nothing will be made."*

That sentence is true. There is no row anywhere in the system saying which
company makes the ads. No migration creates one, no seed creates one, no screen
creates one. There is no screen anywhere in the CRM that can create one.

**6. He presses "Run queued jobs now" anyway.** He gets: *"Tried 1 job: 0
worked, 1 did not. It did not work, and nothing was made. No ad-making service
is switched on for this account, so there is nothing to make the work."*

**The story stops here.** Everything after this point - the library, the review
queue, approve and reject - is machinery for handling ads that were never made.

**7. And if that were all fixed?** Suppose the switch is on and an ad-making
company is set up. A job runs and succeeds. What Chris sees in the Creative
Library is a card with a grey diagonal-striped box saying **"no preview
available"**, the words "static", a date, and a short reference number.

**This is the part the first version of this report got wrong**, and it was the
headline. It said the table that holds creatives has no column for a picture.
It does have one. Here is the real picture, in three parts:

- **The written words are thrown away.** True as first reported. There is no
  column for ad copy. When copy is generated the words are used once to check
  them against the compliance rules and are then dropped. Nothing keeps them.
- **The picture's address IS kept.** The creatives table has had a column for
  it since the very first Creative Factory migration, and the ad-making code
  fills it in on every picture and every video. The database even enforces that
  the address starts with the right partner's folder. So this half was already
  built and built carefully.
- **But nothing ever puts a file at that address.** No part of the system
  uploads the picture anywhere. The address is a shelf label with no shelf
  behind it.

So Chris still sees a striped grey box. But the reason is not "there is nowhere
for an ad to be kept". It is: **the words are dropped, the address is kept, and
nothing ever uploads a file to that address.**

There is a fourth reason on top of those, and it is a one-line bug. See the
next section.

## TASK 3 - empty states and error states

This is the strongest part of the screen. Somebody has clearly been through it
with care. The rules it follows:

- A failed read never shows a zero. Every panel says *"This could not be
  loaded just now"* plus a plain sentence about why, plus *"Nothing is shown,
  rather than an old or made-up number."*
- The count on a filter chip disappears entirely when the read failed, rather
  than showing 0.
- With no partner chosen, nothing is requested at all and every panel says
  *"No partner selected. Nothing is loaded."*
- Server error words are never shown. There is a translator turning
  "not_found", "suite_off", "unauthorized" and nine others into plain
  sentences. Anything it does not recognise gets the screen's own neutral
  sentence rather than a guess.
- The stored failure reason on a job is also translated. The commonest real one
  literally tells the reader to add a database row; the screen replaces it with
  *"No ad-making service is switched on for this account... Trying again will
  not help."*

**What is missing or wrong:**

| Gap | What Chris sees |
|---|---|
| **A safety filter is eating the one flag the screen needs** - NEW, and it is the real reason a preview can never appear | The library endpoint deliberately does not send the picture's address, because an address is a key and keys should not leave the server. Instead it sends a plain yes/no - *does this creative have an address?* - and its own note says that is "all they need to decide whether to render a thumbnail". But every list answer passes through a safety filter that strips anything whose name contains "storage_key" - and the yes/no flag is named `has_storage_key`, so the filter eats it too. The filter has a short list of names it lets through; this one is not on it. The screen's own note names this problem out loud. **So the screen is never told whether a picture exists and always draws the striped grey box.** One line fixes it: add the flag's name to the allowed list. |
| **The test that should have caught it does not** | There is a test asserting the flag comes back as a yes/no. It passes, because it calls the database query straight and never goes through the part of the code that does the stripping. |
| **Fixing that one line still shows nothing** | Because nothing uploads a file (Task 2, step 7). After the fix, the flag would say YES for every picture and video ever made, and every one of those addresses points at nothing. So the fix must land together with real uploading, or the screen swaps a truthful "no preview" for a broken image. |
| **No loading state** on five of the six panels | A page of empty white boxes on every open, until two network calls finish. §6 says never a blank screen. |
| **Empty states offer no next step** | "No assets match this filter for this partner." even when the partner has never had a single creative and no filter is on. It reads as if something is hidden. §6 asks for "what will appear here + one action to make it appear." |
| **Brand kits will always be empty** | Nothing anywhere in the whole product creates a brand kit. Not a screen, not an endpoint, not a seed file, not a background job - only tests. So this panel says "No brand kits match this filter" forever, and the "Brand kit" filter above the library will only ever offer "any". |
| **Two real errors are misleading, not one** | The Approve dropdown lists archived creatives, marked "· archived". Approving one is refused by the server with a sentence rather than a code, so the screen's translator does not recognise it and Chris gets *"The server would not do it... Try again in a moment."* Trying again will never work. **The same fault happens a second time**, and the first version of this report missed it: when the creative is not there at all, the server also sends a sentence instead of a code. The screen has a perfectly good plain-English answer ready for that case - *"That item is not in the list any more. Reload the page to see what is there now."* - and it never gets used. Both need the server to send its short code instead of its sentence. |
| **"Send it back" reason goes nowhere** | The screen is honest about this - it says the reason is kept with the brand, is not sent to the partner, and their own screen does not show it. Honest, but it means the button does half a job. |

## TASK 4 - breaks against UI-STANDARDS.md that a person would notice

**1. The screen's text sizes are all thrown away. §12.7, §3.**
This is the big visual one. There are 64 text sizes written into this file.
**Every single one of them already uses the proper shared size names** - not one
is a hand-typed number. The first version of this report called them
"hand-written", which was wrong and would point a fixer at replacing them with
shared names, which is exactly what they already are. That change would do
nothing.

The real fault is the one the standard describes: the app frame forces
everything inside it to ignore its own size and inherit the size around it. A
proper shared size name dies exactly the same way a hand-typed number would.
The standard allows one escape hatch - a forced rule that wins anyway - and
**this screen writes none.** What survives: the five big numbers at the top,
anything marked as a badge, label, caption or fixed-width type. What is
silently thrown away and renders at ordinary body size instead:

- The big counts on the five "What each job state means" tiles - meant to be
  large numbers, they come out the same size as a sentence.
- Brand kit names - meant to be a heading, come out as body text.
- Every heading inside the slide-out detail panel ("The basics", "Preview",
  "Disclosure flags", "Why it was stopped") - meant to be small grey labels,
  come out the same size as the text underneath them.
- The AI-generated / Synthetic performer pills on every creative card.
- The whole block-reason card: the reason, its reference code and its extra
  detail all come out identical, so the hierarchy is gone.

Effect: the screen reads flat. Nothing looks more important than anything else
except the top row of numbers.

**2. Menu row a role cannot see. §4.**
The standard says a user never sees a nav item they cannot use. This is the
reverse fault and it is worse: the screen works, the owner is allowed on it,
and there is no way to reach it by clicking. Even while you are standing on the
screen, the highlighted "you are here" row in the menu is hidden.

**3. Buttons wired to nothing. §5.**
The five job-state tiles in the Reference section. Hand pointer, hover
highlight, no behaviour. "Every visible control works" is a hard rule and this
is a straight break - and the same file shows somebody already applied that
rule to the tiles at the top of the page.

**4. The five job-state tiles stay four-across on a phone. §11.** NEW.
This is the layout that breaks, and the first version of this report missed it
and praised the opposite. The brand stylesheet forces those five tiles into
four columns with a rule that cannot be argued with. The screen's own rules -
drop to two columns on a small laptop, drop to one on a phone - are polite
rules, so they lose. The brand stylesheet then has a rescue block for phones
under 390 pixels wide that puts things back into one column, but the list of
things it rescues **does not include these tiles**. So on a phone the five
tiles are squeezed four to a row, each about 90 pixels wide, with a number, a
title and a sentence of explanation crammed inside - and the fifth tile drops
onto a second row on its own. It looks broken because it is.

The five big number tiles at the top of the page ARE on the rescue list, so
they stack correctly. Only the job-state legend is left out.

**5. The primary action is buried. §1.**
"The screen's job must be doable without scrolling on a 13-inch laptop." Two
full cards - Partner scope and Monthly writing allowance - sit between the top
of the page and the Enqueue button, on top of the five-number row. On a 900px
laptop screen the one button that makes an ad is at or below the fold.
UNVERIFIED as an exact pixel measurement - I did not open a browser. The
ordering is certain from the file; the exact fold line is not.

**Not a break, worth recording:** status colours are fine. An older note in my
memory said white-label brands overwrite the alert/warn/ok/info colours and
turn every badge one shade. That was fixed on 2026-08-31 and the four colours
are now left alone deliberately. The badges on this screen will read correctly
on a partner's brand.

## TASK 5 - is it finished, or is it a shell?

**It is finished work, not a shell.** That needs saying clearly, because three
"not built" reports in this repo today turned out to be wrong.

Held against `pipeline.html`, the screen the standard calls the reference:

**Where it matches or beats pipeline:**
- Panels use the standard card shape and take the shared shadow correctly.
  No hand-rolled shadow at rest, no border removed from under a shadow.
- It never invents data. No sample rows, no placeholder numbers, no "coming
  soon" panels. When a read fails it says so and shows nothing.
- Its plain-English translation of server errors is better than most screens in
  this app. It refuses to print the server's own wording on purpose, because
  that wording is written for a developer.
- Its comments are unusually honest. It says out loud where a thing is not
  wired, where a reason is not delivered, and where a count can only saturate.

**Where pipeline is ahead:**
- Pipeline paints "Loading the board..." into the page itself, so there is
  never a blank moment. Creative Factory does that for one panel out of six.
- Pipeline is reachable from the menu. This screen is not.

**Phone layout - corrected.** The first version of this report praised this
screen for handling phones properly, one column. That praise is withdrawn. The
screen *asks* for one column and is overruled by the brand stylesheet on the
job-state tiles, which stay four-across at every width including a phone. See
Task 4, item 4. The rest of the phone handling is genuinely good - the tables
scroll inside their own box, the top bar wraps onto two lines, and the library
and brand kit grids do drop to one column.

**The real difference is not the screen. It is what is behind it.**
Pipeline is a window onto data that exists - real clients, real stages. Creative
Factory is a window onto a factory floor with no machines in it, a shelf label
with nothing on the shelf, and a piece of tape over the window. The glass is
clean. There is nothing behind it yet.

## What would actually unblock Chris, in order

1. **Put the row back in the menu - in three places, not two.** Take
   `creative-factory.html` off the hidden list in `public/app/shell.js`, off the
   matching list of addresses in `public/app/crm-sidebar.css`, **and** remove or
   narrow the rule in that same stylesheet that hides the whole Marketing
   section. All three, or it stays invisible. Doing only the first two - which
   is what the first version of this report told you to do - changes nothing at
   all, because the third rule hides the section the row lives in. There is a
   note in that stylesheet warning about the first trap; nothing warns about the
   third.
2. **Stop the safety filter eating the preview flag.** One line. The filter that
   strips storage keys also strips the harmless yes/no flag named after one, and
   that is why the library can never draw a picture. Add that flag's name to the
   filter's short allow-list. **Also fix the test**, which currently passes
   because it skips the filtering step entirely.
3. **Actually upload the file.** The address column already exists and is
   already filled in correctly on every picture and video. What is missing is
   the part that puts the file where the address says. Until that exists, fix 2
   turns "no preview available" into a broken image - so 2 and 3 ship together.
4. **Give the written words somewhere to live.** A column for ad copy. This is
   the one part of the storage story that genuinely does not exist, and it is a
   schema change, so by the house build order it comes before any screen work.
5. **Show the ad on the screen.** Once 2, 3 and 4 exist, the library can show
   real words and real pictures instead of a striped grey box.
6. Set up at least one ad-making service, with real web addresses instead of
   the made-up `api.example-*.com` ones in four of the five.
7. **Make the server send codes, not sentences,** on the two refusals it gets
   wrong - approving an archived creative, and acting on one that is not there.
   The screen already has the right plain English ready for both.
8. Small fixes: make the five legend tiles plain boxes; add those tiles to the
   phone rescue list so they stack on a phone; remove "resize" from the Kind
   dropdown until a parent can be picked; add shape and version-count to the
   Generate box; add the one forced text-size rule the standard allows so the
   screen gets its hierarchy back; and tell people where the on-switch lives
   when the buttons are off.

**COMPLIANCE REVIEW REQUIRED** is not raised. Nothing here changes dispute
logic, credit-repair wording, fee timing, refunds, payment rails, consent
capture or credit-pull type. The compliance rules this screen displays are
read-only and were not touched.
