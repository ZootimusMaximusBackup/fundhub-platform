CF-01 / PARTNER SCOPE
staff · named partner
sets ?partner_id= on all four reads
—

Every query runs inside withPartnerScope, so the RLS policies from 045 supply the partner_id predicate — the SQL in api/creative/* carries none. Outside that scope the same SQL returns zero rows rather than every partner's, which is why there is no roll-up, no leaderboard and no partner-vs-partner view anywhere on this screen.

A partner session cannot name another partner. resolvePartnerId pins a partner principal to its own id and ignores a query-string partner_id rather than rejecting it — rejecting would confirm a guessed id to a prober. A staff session with no ?partner_id= gets HTTP 400 partner_id_required.

CF-03 / JOB STATES & RETRY
four statuses, exhaustive
Retry, as the engine actually models it
claim() → attempt = attempt + 1, status = 'running'
fail(retryable) → status = (retryable AND attempt < 3) ? 'queued' : 'failed'
finished_at := now() ONLY when status becomes 'failed'
run() success → error := NULL, status := 'succeeded'
Constants
DEFAULT_MAX_ATTEMPTS = 3 · provider calls per claimed job
BASE_BACKOFF_MS = 500 · doubling → 500ms, then 1000ms
job-level ceiling = 3 claims before 'failed'
concurrency fallback = 3 when no settings row exists
src/creative/generate.mjs:31-32 (constants) · :102 (claim increments attempt) · :136-149 (in-process backoff) · :151-157 (degrade to queued) · :172 (error cleared) · :253-267 (fail / finished_at) — db/migrations/045_creative_factory.sql:319 (generation_jobs_error_ck)
A queued job may carry started_at and an error. That is a retry, not a run in flight — fail() only stamps finished_at when the status becomes failed. Treating a non-null started_at as "currently running" mislabels every requeued job, so this screen keys the pill off status alone.
attempt is not "retries remaining". It counts claims, and the in-process provider retry loop (3 calls, 500ms then 1000ms) is a separate count that is never persisted. There is no progress, ETA, percentage or queue position column — spec->'variants' is frequently NULL, so there is nothing to compute progress against.
The per-partner concurrency cap is not readable here. claim() reads partner_module_settings.max_concurrent_jobs (column default 3, CHECK 1–20) and falls back to 3 when the row is missing, but none of the four creative endpoints returns that table — so the cap is shown above as the engine fallback, not as this partner's configured value. Same for weekly_asset_target (default 15, CHECK ≥ 15), which no code in the repo reads at all.
CF-04 / CREATIVE LIBRARY
—
There is no preview and there never will be from this endpoint. storage_key is not selected, there is no signed-URL route in api/, and storeAsset() throws away the provider's source_url — creative_assets has no url, thumbnail or meta column.
Not even the boolean arrives. library.mjs:40 selects (storage_key IS NOT NULL) AS has_storage_key, but partnerReadHandler returns page(), page() runs redact() over every item, and FORBIDDEN_KEY (read-api.mjs:18) carries an unanchored storage_key alternative that matches the substring inside has_storage_key. ALLOWED_EXACT (:22) whitelists only ssn_present and has_ssn. So the derived boolean is stripped along with the column it describes: this screen cannot tell whether an object exists for a row, and every tile below is the same placeholder rather than two placeholders pretending to know the difference. creative-endpoints.pg.test.mjs:107-118 asserts the boolean is a boolean, but it calls fetchRows directly and never goes through redact() — which is why CI is green on a field no screen can receive.
A copy card cannot show its copy. storageKeyFor() returns NULL for kind = 'copy' because copy lives in the row, not object storage — the tile says so from kind, which is returned, not from a storage flag. And there is no text column on creative_assets: the generated words exist only in compliance_screenings.screened_text, which no endpoint returns.
?kind= and ?format= fail silently by design (library.mjs:29-32 — "a stray value should not blank the screen"). An unrecognised value is dropped and the unfiltered result comes back with HTTP 200, so an unchanged result set is not proof the filter applied. ?state= is different: an invalid value throws BAD_STATE, which partnerReadHandler's generic catch turns into HTTP 500 {ok:false, error:'query_failed'} — not a 400.

CF-06 / REVIEW & APPROVAL QUEUE
ItemStateSubtypeDetailReasons BudgetOfferPlatformFlagsUpdated
Two shapes in one list, and the row is asymmetric. For an creative_asset row, subtype is the kind and detail is the format; budget_cents, offer_type and platform are NULL. For a campaign row, subtype is the (nullable) strategy_key and detail is the campaign name; ai_generated and synthetic_performer are NULL. Nulls are rendered blank here, never as false or $0. Updated is updated_at on both branches — the asset branch selects no created_at at all, and the whole UNION is ordered q.updated_at DESC, so these are not the timestamps CF-04 shows.
A campaign's reasons is not a reason list. It is a synthesised jsonb_agg of {code: <screening state>, message: <the whole reasons ARRAY>} — one element per compliance_screenings row, with a nested array where a string would be. A naive renderer prints [object Object]; this one unwraps it. Asset rows carry the real blocked_reasons array instead.
This filter fails silently. approvals.mjs does not use stateFilter — an unrecognised ?state= makes both branch predicates false and returns an empty list with HTTP 200. There is no 400 to react to, so "empty" and "wrong filter" look identical.
Approval is tracked on the campaign, not the asset (generate.mjs:233-235). There is no per-asset approve or reject — and no route to perform either; the queue is a worklist, and the decision is recorded against campaigns.approval_state elsewhere.
approval_state is a workflow value, not a verdict. The campaign branch selects on approval_state = 'awaiting_approval', which says a human has not moved the row yet — it does not say what compliance thought. A partner with approve_before_launch off gets screenings that come back passed and campaigns that still sit here until someone clicks; a partner with it on gets needs_approval on every non-credit-repair subject, because screen.mjs:215 reads one per-partner boolean and cannot disagree with itself between two campaigns of the same partner.
CF-07 / BLOCK REASON CATALOGUE
CodeRule setMatchSeverityApplies toCitation
Every code this screen can render, from all three sources. Twelve are compliance_rules rows seeded by 047. Eight are built in code by src/compliance/screen.mjs. Nine more come from src/compliance/targeting.mjs, which screen.mjs:154-157 splices into the verdict for a meta campaign payload — those nine reach this screen through the campaign screenings in CF-06 and can never appear in an asset's blocked_reasons, because generate.mjs screens an asset with no targeting key. Seventeen of the twenty-nine exist in no table at all. A reason object is {code, rule_set, message, citation?, severity?, detail?} — no timestamp, no reviewer, no id, no resolved flag. There is nothing to build a review-history timeline from.
Only a compliance_rules row has a severity. The column is CHECKed to block or warn (047:75) and all twelve seeded rows ship as block. The seventeen code-built reasons have no severity key at all — r() (screen.mjs:251) and reason() (targeting.mjs:162) do not set one — so the Severity column reads null for them rather than guessing a value. What decides the outcome is hardBlocks (screen.mjs:200), which counts anything whose severity is not warn: an absent severity blocks. There is no gate severity anywhere in the schema or the engine; the two approval codes are returned from a different branch, not with a different severity.
Two gates are structural and have no override. TikTok + credit_repair is rejected before any rule row is read (screen.mjs:132), by CHECK campaigns_tiktok_credit_repair_ck, and by a rule row that exists only to produce a readable message — deactivating the rule does not open the door. Credit-repair creative always requires a human whatever approve_before_launch says; that branch does not consult the setting at all.
screen_error is a platform fault, not a copy fault. Screening fails closed on any error — no database, bad regex, malformed subject — and returns blocked with the partner-safe message "Compliance screening could not complete, so this is blocked. Try again; if it persists this is a platform fault, not your copy." Treat it as an incident, not a rewrite.
Eleven codes will never appear on an asset. The two approval codes come back with state needs_approval, and generate.mjs writes blocked_reasons only when the verdict is blocked — otherwise []. The nine targeting codes are never evaluated for an asset at all. All eleven live in compliance_screenings.reasons, which has no endpoint of its own; the only way they reach a screen is the jsonb_agg the approvals query builds for a campaign row. Likewise no warn bucket: all twelve seeded rules are block.
CF-08 / BRAND KITS
palette, fonts, voice_profile and products have no schema. They default to {} / [] and no migration or code defines their inner keys, so the cards below render whatever keys each row happens to hold rather than assuming primary/secondary/accent or heading/body. The only jsonb key any code in this module reads is voice_profile.tone (copy.mjs:83, static.mjs:77).
source_url and scraped_at are NULL in practice. Nothing outside tests writes brand_kits or brand_kit_sources — there is no scraper, no re-scrape route, and brand_kit_sources has no endpoint (and a delete-guard trigger). So there is no crawl history, no freshness indicator, no version history, no diff and no restore.
logo_asset_id is a reference, not an image. It points at a creative_assets row whose storage_key never leaves the process. And asset_count counts non-archived assets only, so it will not match a library count taken with ?include_archived=1.

v_creative_config_gaps (048:262, redefined in 052) carries exactly the columns below, but api/ contains only the four creative GET files and none of them selects from it. The rows here reproduce the view's shipped status strings verbatim so the shape is reviewable; they are not a live read. This panel is staff-only by nature — the view is org-level, and RLS does not scope it to a partner.
configdetailrows_setstatusconsequence
Generation cannot run at zero providers. resolve() takes the active creative_providers row for (org_id, asset_kind) with the lowest priority and throws when there is none, rather than falling back to an arbitrary vendor — "falling back would spend the partner's money at a vendor nobody chose". 048 ships with no active row, so that is the state of a fresh database, and a job that hits it fails permanently (retryable false): retrying would not conjure a config row.
No vendor names, endpoints, models or keys. schema only rates unsigned
⚠empty on any real database — and that is correct
creative_usage_events and v_partner_creative_usage exist, but no endpoint serves either, and accrue_creative_usage() is called only from src/social/social.pg.test.mjs — no application code path writes a usage row. So there is nothing to show, and a populated usage panel here would be invented. The grain, if it is ever exposed, is monthly (date_trunc): there is no daily or weekly rollup.

No rows. v_partner_creative_usage has no HTTP endpoint and nothing accrues against it.

The rates are not a partner-facing number. creative_billing_rates is org-level and unscoped by RLS, and the whole reason cost_cents is withheld from the jobs endpoint is to avoid publishing the markup. Rendering a markup percentage, a vendor cost or a derived "you were charged" figure on a partner surface would publish a commercial term that no human has signed — both rates ship with signed_off_at NULL and notes marked PLACEHOLDER.
Billing raises rather than guessing. accrue_creative_usage() raises "creative_billing_rates.<key> is not set — refusing to accrue usage against an unchosen rate" when the rate is NULL. On accrual the rate and unit cost are copied onto the row (rate_pct_applied, unit_cost_cents) so a later rate change cannot restate history; accrual is idempotent on (org_id, partner_id, source_event_id); and a record is voided with a reason, never deleted.
CF-12 / ENDPOINT LEDGER
what this screen can and cannot read
SurfaceSourceStateNote
Generate + run are live. POST /api/creative/generate enqueues; POST /api/creative/run (and the creative-job-runner cron every 2 minutes) claim and run jobs. Provider credentials (CREATIVE_*) must be set for assets to render — otherwise the job fails or requeues with a clear error.
Approve / Reject / Archive — expand a row in the review queue (CF-06) or use asset id below. Writes POST /api/creative/actions.
Archive sets archived_at — library ?include_archived=1 then includes those rows. Approve sets compliance_state='approved'; reject sets blocked with a reason.
No human names. requested_by, approved_by and created_by_agent_id are uuids, and none of the four endpoints joins accounts or agents — jobs.mjs does not even return requested_by, and library.mjs does not return created_by_agent_id. "Requested by Jane" cannot be rendered, so it is not.
No performance data on a creative. creative_assets has no impressions, clicks, CTR, spend, ROAS, frequency or conversions — ad performance lives in ad_metrics_daily keyed by ad_id (046) and no creative endpoint joins it. A "top performing creative" panel cannot be built from these APIs; the fatigue and spend surfaces on Campaigns are where that data lives.
