HR-01 / THE HUMAN GATE
advisory only read-only · GET

Scores are advice. People decide.

Scores are advisory. No candidate may be rejected without a named human and a written reason; the database enforces this.
That sentence is the scoring_notice string api/hiring/application.mjs returns on every application, and it is printed again beside the score history in the review drawer. Every row on the board carries its own recommendation_status — the literal “advisory — a human decides” — for the same reason.

Enforced in three places, not one

  1. reject() refuses without decidedByStaffId and a non-blank reason — src/hiring/pipeline.mjs:212-227
  2. hiring_decisions_human_ck requires both on reject and offer_declined; hiring_decisions_offer_ck requires a named human on offer — 051 §H
  3. trg_application_terminal refuses status='rejected' unless a reject decision naming a human already exists — 051 §H
There is no auto-reject, no score threshold that closes an application and no rejection-reason picklist: reason is free text. Recommendation pills on this screen are deliberately all one colour — a traffic light turns advice into a verdict, which is exactly what the grader refuses to be.

HR-03 / PIPELINE BOARD
—
Columns are the eleven seeded rows of pipeline_stages where pipelines.key = 'hiring', in sort_order (051 §A). mock_call is not among them — doc 9 retired it and the migration deliberately does not seed it, though it survives as a legal hiring_rubrics.stage_key. The board is not draggable: the API has no route that moves a card.
Stage and status are different columns and they legitimately disagree. The ?state= filter matches the stage key, never candidate_applications.status; there is no way to filter on status at all.
The Hired stage is a trap, and the board shows it. advance(toStageKey:'hired') flips status to hired (pipeline.mjs:196-199) and advance() then refuses any application whose status is not 'open' (pipeline.mjs:179-181) — so a row that enters Hired is frozen there permanently. Nothing else in the repo writes status or stage_id; the only two writers are pipeline.mjs:196 and :249. Onboarding, Ramp and Performing are therefore reachable only by advancing straight past the Hired stage, which leaves status open — which is exactly what the three rows there show, and why rampReview’s status = 'open' gate can ever match. Bethany Cole is the other case: she went through Hired and cannot be moved again. Do not count “active employees” from either column.
The score block always travels together — average, recommendation, rubric version and flag count in one place, captioned with the row’s own recommendation_status. The board carries the latest score only (a LATERAL … LIMIT 1); the full history is on the application, so there is no trend line here to draw. has_video and has_resume are booleans on this endpoint — candidates.mjs:48-49 reduces both to IS NOT NULL, so the board has no thumbnail, no transcript and no duration. The review drawer is built from api/hiring/application.mjs, which returns a.video_url in full and links it; the resume stays a boolean everywhere because resume_document_id is never returned by either endpoint.
HR-04 / NEEDS A HUMAN
— ?flagged=1
CandidateRoleStageStatus AverageRecommendationRubricWhy it is hereIn stage
The endpoint predicate is exactly jsonb_array_length(COALESCE(sc.flags,'[]'::jsonb)) > 0 OR sc.average IS NULL — flagged, or unscorable. The COALESCE is load-bearing: the score arrives through a LEFT JOIN LATERAL, so without it an application with no score at all would make the first arm NULL rather than false. A null average is rendered as not scored, never as a low score: grade() returns average: null and recommendation: 'incomplete' the moment any category is unrated, because banding the three categories somebody happened to fill in is how a candidate gets “below bar” from one answered question.
?flagged has no status filter, so closed applications keep appearing here until someone re-scores or the window moves. They are dimmed rather than hidden — the endpoint returns them and pretending otherwise would misreport the queue.
HR-05 / JOB POSTINGS & SYNDICATION
PostingRoleChannelLocationStatus PublishedPostedApplicationsLast 7dLast synced
⚠ CONFIRM BEFORE THIS RUNS LIVE. Both src/hiring/linkedin.mjs and 051 §I carry that marker: Talent Solutions is partner-gated and the payload shapes are unverified against a real account. Treat every LinkedIn row as an unconfirmed integration, not a working one. There are no impressions, views, clicks or apply-rate numbers anywhere — LinkedIn analytics are not modelled.
Applications and Last 7d count job_posting_id, not source. Both are correlated subqueries on candidate_applications.job_posting_id (api/hiring/postings.mjs:36-40), the second one narrowed to applied_at > now() - interval '7 days'. They reconcile row-for-row with HR-03 — and they are small, because only 6 of the 24 applications on the board came through a posting at all. Referrals, ads and the client base arrive with job_posting_id NULL and are counted here nowhere. The two columns are independent: A-1064 applied through fundhub.ai/careers/closer, which is P-002’s apply_url, so he counts against a LinkedIn-channel posting while his candidates.source reads inbound. A posting with a zero here is not broken — nobody has applied to that req.
last_error is the platform’s own message, token-scrubbed and sliced to 1000 characters, and it is shown verbatim — paraphrasing it into “posting failed” removes the one detail that makes it fixable. It is the response body alone: postJob stores err.platformMessage (linkedin.mjs:140), which is set from the raw body (:85) and wins over the prefixed err.message whenever there was one — so no LinkedIn <status>: prefix is ever stored, and the HTTP status only appears if the platform put it in its own JSON, or as the literal HTTP <status> fallback when the body was empty. That also means retryable is not persisted anywhere: it is computed as HTTP 429 or ≥ 500 (linkedin.mjs:87) and returned to the caller, so a failed row here cannot tell you on its own whether a retry is worth it.
No connection panel. hiring_channel_connections is joined by no endpoint — connection_state, token_expires_at and scopes are unavailable here, and the connection’s own last_error is a different column from the posting’s. Postings also return no description and no external_id, only is_published, so there is no job body to render and no deep link to the live post. Nothing schedules postJob / closeJob / ingestApplications, so there is no “auto-posting” or “next sync” to report.
HR-06 / FUNNEL BY SOURCE
—
SourceRoleApplications Currently at or past group interview Currently at or past 1:1 Currently at or past offer HiredRejectedHire rate %
These are current-stage counts, not historical progression. The endpoint filters on the application’s present sort_order — >= 2, >= 3, and >= 4 AND stage_key <> 'rejected' — so someone sitting in Not Moving Forward (sort_order 9) is counted in both “at or past group interview” and “at or past 1:1”. Calling these stage conversion rates would be a lie, so the headers say what the SQL says.
hired and rejected come from candidate_applications.status, not from a stage — and status = 'hired' is set by exactly one thing, advance(toStageKey:'hired'). Anyone advanced past the offer without passing through the Hired stage keeps status open (see HR-03), so this column undercounts hires and is a count of applications parked in the Hired stage rather than of people working here. hire_rate_pct is round(100 · hired / applications, 1) and is NULL when applications = 0. ?days defaults to 90 and is clamped to 1–730. No stage-by-stage drop-off chart exists: v_hiring_funnel has no endpoint and nothing records stage-entry history, so time-in-stage across the funnel cannot be computed.
HR-07 / DECISION LOG · AEDT AUDIT TRAIL
WhenDecisionMoveRoleSource Decided byRecommendation at decisionScoreFollowed?
Advances are logged too, not just rejections. An audit that only records rejections cannot answer how differently similar candidates were treated, so advance() writes a hiring_decisions row as well (src/hiring/pipeline.mjs:186-193). Neither application_scores nor hiring_decisions can be deleted — hiring_no_delete raises on any DELETE.
followed_recommendation is defined only for reject, advance and offer, and is NULL whenever recommendation_at_decision is NULL. It is NULL by design for offer_accepted, offer_declined, withdraw and hold — and those four, plus the Withdrawn stage and status, have no producing code path in pipeline.mjs at all, so expect them to stay empty.
score_at_decision and rubric_version resolve through d.score_id, which pipeline.mjs leaves NULL unless the caller passes one — blanks here are normal, not missing data. candidate_notified_at exists but nothing ever sets it; the feedback obligation becomes a task (hiring:feedback:<applicationId>, source_workflow hiring-candidate-feedback) that no hiring endpoint exposes.
No row here can be traced to a candidate. The projection (api/hiring/decisions.mjs:41-58) carries no d.application_id and no name from candidates — only c.source and r.key, which are the columns an adverse-impact comparison needs and the smallest set that identifies nobody. So there is no “open this application” control in the expanded row: the join runs the other way, from api/hiring/application.mjs (WHERE d.application_id = $1), and HR-08.6 in the drawer is where the two meet.
