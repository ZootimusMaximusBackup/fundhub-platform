publishDue reads status = 'queued' AND scheduled_for <= now(), ordered by scheduled_for, LIMIT 50 per invocation. A row whose channel is not active is skipped with { skipped: 'channel_not_active' } — the post stays queued and attempt is not incremented. A row with scheduled_for IS NULL is never due and will sit here forever.
A blocked post is stored with its reasons, not rejected and forgotten — social_posts_blocked_reason_ck forbids an empty reason list. It is also terminal: nothing in the repo re-screens an existing post, and schedule() only ever INSERTs a new row. Fixing the copy means composing a new post in SS-03. There is no unblock, no override and no exception request — screen.mjs has no force argument and none may be added.
No engagement figures appear here because none exist. ad_metrics_daily.ad_id is NOT NULL and references ads, so it cannot hold a row for a social_post, and there is no organic metrics table anywhere in the schema. Organic posting is also never metered: creative_usage_events.event_type is CHECKed to generation | managed_spend and has no social_post_id.
One row is written before every platform call, so a crash mid-post leaves a findable record: actor 'agent', target_type 'social_post', rule_key 'social_publish'. agent_id comes from publishDue's agentId parameter, which defaults to null — nothing in the repo passes one, so it reads null here. revertible is the API's computed undo_payload IS NOT NULL AND undone_at IS NULL; the payload itself is never returned. It says a revert is recorded as possible, not that one would work: the payload is {action:'delete_post'} and no social delete implementation exists.
