The source vocabulary is public/app/data.js's, but the values in this column are assigned by this file: FHData exposes readers for /api/read/* and /api/dashboard/* and none for /api/campaigns/*, so the same { ok, source, data, error } envelope is reproduced here rather than reaching into its private get(). api (real rows) · demo (demo session, nothing queried) · unauthorized · nodb · offline · notfound · badrequest are all reproduced faithfully; nodata is data.js's and is never reached from here, because these panels always have something to ask about. One name in the column is this screen's own state, not a reader outcome: … while a fetch is in flight, or before a panel has been read at all. There is no built-in data on this screen. A panel that cannot be read shows an empty or error state saying so — it never keeps rows from a read that did not answer, and it never stands in numbers of its own.
A bad filter is a 500, not a 400. stateFilter throws on an unknown ?state= and partnerReadHandler's catch returns 500 { ok:false, error:"query_failed" }. /detail with no id does the same. The only 400 these endpoints produce is partner_id_required — a staff session that has not named a partner. So a 500 here may be this screen's own bad query string rather than a backend outage.

CM-03 / TODAY'S SPEND VS CEILINGS
ScopeCampaignPlatformDaily limit Spend todayHeadroom% of ceiling Max daily increaseFlags
This is our mirror, not platform truth. spend_today_cents comes from ad_metrics_daily where date = CURRENT_DATE — the same number the pre-flight budget check uses. The kill switch deliberately reads the platform instead, so a sync failure that made this look healthy cannot also disable the last line of defence. Green here is not proof spend is under control; breached_at, stamped by runKillSwitch from platform truth, is the column that is.
Do not add these rows up. The scopes overlap by design — a partner ceiling, a platform ceiling and a campaign ceiling can all count the same spend, and checkBudgetWrite evaluates every matching scope rather than only the tightest. approaching_ceiling is pct_of_ceiling >= 80 and exhausted is headroom_cents = 0; both are named in the endpoint SQL, so this screen is not choosing a threshold. headroom_cents is GREATEST(limit − spend, 0) and never goes negative — the overspend shows up in pct_of_ceiling instead.
CM-04 / CAMPAIGNS
CampaignPlatformOfferApproval state StrategyBudget / daySpend yesterdayROAS 7d Ad setsAdsDisclosureStatusSynced
approval_state is the state this screen means — draft · awaiting_approval · approved · live · paused · archived, the six values of campaigns_approval_ck, and the only thing ?state= filters. The status column beside it is a nullable free-text mirror of the platform's own status string with no writer anywhere in the repo, which is why it reads — on every row. synced_at is the same story: a real column with no sync job behind it — until you click Sync Meta now, which calls POST /api/campaigns/sync and writes synced_at.
spend_yesterday_cents is CURRENT_DATE − 1, on purpose — today's is partial, and a list judged on it makes a campaign that started at 11pm look dead. There is no today's-spend-per-campaign number anywhere in the API: today's spend exists only in CM-03 and only per ceiling. roas_7d is avg(ad_metrics_daily.roas) over date > CURRENT_DATE − 8 and is null until a campaign has metrics. strategy_key arrives as the raw key — campaign_strategies (display names, skeleton) is exposed by no endpoint.
No deep links. Neither list nor detail selects campaigns.external_id, so a "view in Ads Manager" link cannot be built. Only connections carry an outward id (external_ad_account_id, external_business_id) — see CM-07.
CM-06 / CREATIVE FATIGUE BY AD
AdCampaignPlatformSpendImpressions FrequencyCTRROASLast dateRotated Next rotationRecommendation
The recommendation is the optimiser's, not this screen's. api/campaigns/fatigue.mjs reads optimization_rules from the partner's org — the same rows src/optimize/rules.mjs reads — and returns only the derived word: refresh · queue · ok · unconfigured. The thresholds are deliberately not in the response, so nothing here prints a number the API did not send. An inactive rule yields no recommendation rather than a default one, and unconfigured means both the frequency and CTR rules are off — which makes it all-or-nothing across every row, never a per-ad verdict.
Absence is not health. These rows INNER JOIN ad_metrics_daily, so an ad with no rows in the window simply is not here. frequency, ctr and roas are unweighted averages of daily values, not impression-weighted. ctr is stored in the platform's own units and compared as a bare percent — it is not a 0–1 ratio. hours_until_next_rotation is null when ads.rotated_at is null or the CTR rule is inactive. There is no fatigue score, no health index and no creative preview: creative_assets.storage_key never leaves the process and no campaigns endpoint returns ads.asset_id.
CM-07 / PLATFORM CONNECTIONS & LAUNCH BLOCKERS
PlatformAd accountConnection stateVerification TokenCampaignsCan launchCredit offerBlockers
The launch gate is in the database, not in this screen. trg_campaign_launch_gate refuses approval_state = 'live' unless the connection is active and — for all three offer types, funding included — platform_verification_state = 'approved'. That is exactly what can_launch and can_launch_credit_offer encode. Business verification is done in the platform's own Business Manager; there is nothing to click here.
No token exists client-side in any form. Only the encrypted columns exist, connections.mjs does not select them, redactConnection strips them again, and safeMessage() rewrites any ciphertext that reaches an error string. What you get is presence — has_access_token / has_refresh_token — and expiry. A null token_expires_at makes token_expired false; that means unknown, not "valid forever". There is no OAuth URL, no required-scopes list and no reconnect link in the response, so this screen offers none.
A blocker is written per CAMPAIGN and shown per connection. These are unresolved partner_onboarding_tasks rows — connection_not_active · verify_business · link_croa_disclosure — and checkLaunchReadiness writes each one against both the connection and the campaign it ran for (the open-task unique index is partner_id, task_key, connection_id, campaign_id). The connections endpoint joins on connection_id alone and does not project campaign_id, so the same task_key can appear once per blocked campaign on the same connection, and the wording gives it away: the detail text names that campaign's own offer_type. What you cannot get from this response is which campaign — that column is not returned, so this screen does not name one. Severity is blocker or warning in the CHECK, but checkLaunchReadiness passes none of the three and openOnboardingTask defaults to blocker, so every row here is one. The check runs over one campaign at a time and emits every blocker that campaign has, so a connection showing one of two applicable blockers would mean the check never ran.
google is a legal platform value everywhere, but adapterFor('google') throws — it has no write adapter, so a Google row here is a connection, not a controllable channel.
CM-08 / ACTION LOG
WhenActorTargetRuleReason ChangeOutcomeRevert
action_log has no status column, so the outcome on each row is derived from four columns and nothing else: undone_at → reverted · execute_error → failed · executed_at IS NULL → logged, never executed · otherwise executed. "Pending", "queued", "in progress" and "attempt 2 of 3" would all be invented — errors are classified as retryable in _api.mjs but nothing in this repo retries or records an attempt.
Every kill_switch_ceiling row reads "logged · never executed", and that is the writer, not the outcome. runKillSwitch is the one automated action that does not go through guardedWrite: it INSERTs its own action_log row with no executed_at in the column list and never updates it afterwards, and guardedWrite is the only thing in the repo that stamps that column. The pause itself is not in doubt — the same transaction stamps spend_ceilings.breached_at (the breached flag in CM-03) and runs UPDATE campaigns SET approval_state = 'paused' over the ceiling's scope, which is why the campaign named in this row reads paused in CM-04. It updates campaigns only: the ad sets underneath keep whatever state they had, so a killed campaign with live ad sets under it is the expected shape, not a leftover.
The log row is written BEFORE the platform call and stamped afterwards (guardrail → money → action log → platform, with no way to skip a step). That is what makes "logged but never executed" a queryable state rather than a lost change. Platform errors are stored verbatim, truncated at 2000 chars, into execute_error and — for target_type = 'campaign' — into campaigns.last_error. The table is append-only: DELETE raises, and UPDATE may only touch executed_at / execute_error / undone_at / undone_by.
revertible is a flag, not a button. undo_payload is withheld from every endpoint on purpose, so this screen cannot preview a revert or render its diff — and there is no revert route to call: undo() is a library function in src/adplatforms/index.mjs. Agent rows usually carry no agent_name because runDailyOptimization and runKillSwitch both default agentId to null — the rule_key is the attribution. Human names come from accounts.name, the partner's own users.
